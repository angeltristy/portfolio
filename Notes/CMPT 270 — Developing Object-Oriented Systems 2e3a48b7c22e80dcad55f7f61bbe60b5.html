1 – Object Oriented Thinking

Class: Blueprint or instructions on how to create an object

Object: An instance of a class created in your software application

Field or Attribute

  • Data relevant to the purpose of the system
  • May include the state of the object
Constructor
  • Creates an object with initial attributes
  • Similar to __init__ in python)
Methods
  • Implement behaviours relevant to the purpose of the system
  • Some describe the real world behaviours
  • Some describe system behaviours
Real objects are organized into types
  • Modeling:
    • Objects with similar enough characteristics are considered the same type
    • Degree of similarity depends on the application
  • Programming:
    • Objects of the same type are created to have the same class
    • The class defines the fields and operations
    • All objects of the same type have the same fields and operations
Entity objects: models real things
  • E.g., A tree, a student, a number
  • Concrete Objects:
    • E.g., people, buildings, equipment
  • Conceptual Objects:
    • E.g., Organizations, agreements, abstractions
  • Event and State-Change Objects:
    • E.g., purchase, sale, birth
Container objects: data structure to store entities
  • E.g., A forest, a classroom, a Stack
Interface objects: Communication with the outside world
  • E.g., a file, the console, a printer
Control objects: Organize computations
  • E.g., main program
Methods: Things that an object can do or have done to it.
  • Accessors/Getters : Accesses of calculates a value based on the data stored in, or
  • accessible from, the object
  • Mutators/Setters : Changes the state of the object; does not return anything
  • Hybrid : Both access and mutate; discouraged by modern software approaches
Software Development Process

1. Requirements: Figure out what the software needs to do

2. Design: Device a plan to meet the requirements

3. Implementation: Write the code, according to the plan

4. System Testing and Verification: Show that the system meets the requirements

5. Maintenance: Install, deliver, update, upgrade, etc

2 – UML

Unified Modelling Language – provides standard visual notations for designing a software system.
  • Structural Diagrams: Component, Object, Class, and Deployment Diagrams
  • Behavioural Diagrams: Use Case, State, Sequence, and Interaction Diagrams
UML Class Diagram
  • Provides an overview of the class that make up a software system.
  • Shows different attributes and methods for each class.
  • Shows the relationships between different classes.
  • Akin to a blueprint of a mechanical machine, shows all the individual pieces and how they are connected
  • Does not show the step-by-step functionality of the system (That is captured by a UML Sequence Diagram)
Importance of Class Diagrams
  • Allows developers to model the entire system before going to implementation
  • Making changes is easier on the model than on the implementation
Data Types in UML
  • Boolean
  • Integer
  • String
  • Real
  • Custom Classes
Visibility
  • Public (+): visibile to all classes in the system
  • Private (-): only visible within itself
  • Protected (#): visible to other classes within the same package, and subclasses in other packages
Relationships between Classes
  • Inheritance: Class B inherits from A
  • Interface Implementation: Class B implements A
  • Dependency: Class B depends on Class A
  • Association: A and/or B have an attribute of the other
  • One way association: B has an attribute/class variable of type A
  • Reflexive association: Class A has an attribute of type A
  • Aggregation: A contains an instance of B, B can survive if A is deleted
  • Composition: A contains an instance of B, B cannot exist without A

3 – Object Oriented Design

OO Design Principles:
  • Encapsulation: grouping related variables and functions, reduce complexity, and increase reusability
    • i.e. Classes/Objects
  • Abstraction: hide details and show the essentials; isolate the impact of changes
    • Keep most attributes private
    • Private helper methods
    • Public methods should be the only way other classes can view/interact with your data
    • Use interfaces to group related methods together
  • Inheritance: eliminate redundant code
    • The relationship between a more general class (superclass) and a more specialized class (subclass)
    • Subclasses inherit all public/protected attributes and methods from their superclass (recursively)
  • Polymorphism: refactor ugly if and switch/case statements
    • An object can take multiple forms (types)
    • Static (compile time): method overloading
    • Dynamic (runtime): method overriding through inheritance
Substitution Principle:
  • States that you can always use a subclass object when a superclass object is expected.
Benefits of Polymorphism
  • In Java, method calls are always determined by the type of the actual object, not the type of the variable containing the object reference.
    • This is called dynamic method lookup.
    • Dynamic method lookup allows us to treat objects of different classes in a uniform way.
  • This feature is called polymorphism.
  • We ask multiple objects to carry out a task, and each object does so in its own way.
  • Polymorphism makes programs easily extendable.
Interface
  • An interface is a group of related methods with empty bodies
  • You can program uniformly using an interface type
  • You can defer the implementation to subclasses
  • Helpful for program modification and extension
Abstract Class
  • A class that can be instantiated is called a concrete class.
  • You cannot instantiate an object that has abstract methods.
    • But, you can declare a reference variable whose type is an abstract class.
    • The actual object to which if refers must be an instance of a concrete subclass.
    • This allows for polymorphism based on an abstract class.
Summary
  • A subclass inherits data and behaviour from its superclass..
  • A subclass object can always be used in place of a superclass object.
  • A subclass can override a method defined in it superclass and provide a new implementation.
  • Interfaces can be used to define a group of related methods, allowing polymorphism to work with objects across different inheritance structures.

4 – Java Basics

Java is compiled
  • A compiler translates a program to a machine code executable file ("app")
    • The compiler does not run the app
    • Two steps: compile, then run
  • An interpreter executes a program directly
    • The interpreter does not compile the program
    • One step: run
Native vs Virtual
  • Some compilers create executable files that run directly on the computer's hardware, called native.
    • i.e C, C++
    • Less secure, less portable.
  • Java compiler creates an executable for a simulated machine, called virtual
    • An application called a virtual machine must run the compiled app.
    • For safety
      • A compiled Java app could attack the VM, but not the physical machine.
    • For portability
      • A compiled Java app can run on any computer with the virtual machine installed.
Static vs Dynamic Typing
  • Static typing:
    • Expressions are checked at compile-time
    • Illegal expressions cause compile-time errors
    • You must fix the code before you can run it
  • Dynamic typing:
    • Expressions are checked at run-time
    • Illegal expressions cause run-time errors
    • You can run the program, but it might crash
Java is more detailed to inform the compiler, more structured to improve reusability, and more verbose to remain consistent with C/C++.

The Java platform

  • Users install a Java platform to run a Java app, which includes a Java Virtual Machine (JVM) and a Java API.
    • Application Programming Interface is a large collection of software packages:
      • Graphics, user interface, networking, sound, database, math, and much more
The Java SDK
  • Programmers install a Java Software Development Kit (JDK) which includes a JVM, Java API, as well as a Java compiler and other utilities. Does not include IDE.
Summary
  • Java apps are created by a Java SDK
    • Includes a compiler and other utilities
  • Java apps can be developed using:
    • IDE
    • Command-line tools
  • Java apps are executed by a Java platform
    • Includes JVM and Java API
  • Java was designed to be as close to C/C++ as possible
    • The C language does not have classes or objects
    • C++ adds classes and objects to the C language
    • C/C++ compile to native machine code
  • Why not use C/C++ instead of Java?
    • Portability. Also, pointers

Reference Types

7 – Regression Testing

  • A software bug is an error, flaw, failure, or fault that produces an incorrect or unexpected result.
    • If a program does not behave as expected, this is called a fault which happens for an error or bug.
  • Testing and debugging are processes to ensure a program is correct in the sense that it behaves as expected, producing the correct outputs for given inputs.
    • Testing is a proactive process to identify bugs in your program. You generate test cases or inputs for your program and then check whether your program generates the expected output.
    • Debugging is a reactive process to fix the identified bug. You trace your program step by step to investigate why the bug is happening and to repair it.
Testing
  • The goal of the testing process is to detect all the faults in some code.
  • To achieve this goal, we start by producing a set of test cases.
    • A test case consists of a specific input to the code, or a usage scenario performed under specific conditions.
    • Write test cases for each method in your code.
  • Black box
    • Generate test cases by reading the function signature and its comments.
    • Don't look at the actual code/implementation fo the function
  • White box
    • You look at the actual code/implementation of the function.
  • Both are complementary to each other, no right method for test case generation, you can use both methods
Types of Errors
  • Errors of Commission
    • The code you wrote has errors
    • Syntax errors
    • Minor logic errors
  • Errors of Omission
    • You did not write code for some behaviour
    • No design
    • No plan
Faults
  • Fault: the appearance/form/manifestation of an error
    • Incorrect output
    • Run-time errors
    • Failure to achieve the stated purpose
  • Presence of a fault implies the presence of an error
    • `One error might create many faults
    • An error might create no faults (yet)
    • It's these errors that testing seeks to find
Testing Process
  • Validation: Using techniques to increase our confidence in the system (formal proofs, informal reasoning, testing)
  • Debugging: Deducing the error from the fault
  • Defensive Programming: A practice of writing code to facilitate validation and debugging
Test Coverage
  • You cannot test all possible inputs, you have to create a small number of test cases to reveal all errors
  • Every method, even the most trivial, is invoked at least once. Ensure that it has the correct return value or effect.
  • Multiple test cases should be used
    • To check different return values, different effects
    • Check that linear search finds an item appropriately, and fails to find an item appropriately
  • Test special cases and all error situations
Testing Levels
  • Unit testing: each method, individually
  • Integration testing: some methods working together, limited combos
  • System testing: the entire application, very time consuming, do as much unit / integration testing before this
Test-Drive Development (TDD)
  • Using the specifications only:
    • Design the method stubs: parameters, return, effect
    • Design all test cases before implementing the method
    • Initially all test cases should fail
    • Work on the method implementation until all the test cases pass
  • Advantages:
    • More thought put into methods b/c of test cases
    • You know when you are done writing the method
Bottom-up Testing
  • Approach
    • First test units that don't use any other units
    • Repeatedly: test the integration of modules that only use modules already tested
    • Continue until the whole system has been tested
  • Use for well understood modules (or well-structured assignments)
Top-down Testing
  • Approach
    • Implement the top-level methods first (e.g. iterative refinement strategy)
    • Write test cases for the top-level methods
    • Leave low-level methods as stubs
  • Use for nebulous modules (or open-ended free-form projects)
Regression Testing
  • Comprehensive test scripts created during implementation
  • Rerun whenever a change is made
  • Easy to rerun and verify everything is still correct
  • Never delete a test case, unless the method it tests is deleted
  • If a bug or error is detected, add test cases to test for it in the future (in case the code regresses)
Practical Java Testing
  • In any language, we can do testing with if-statements
  • Modern languages have testing tools developed – not part of the main language.
  • In Java: Junit, beyond the scope of this course
Regression Testing in CMPT 270
  • We will write all Unit tests in the public static void main (String[] args) method of the class we are testing.
  • This allows us to keep the test code close to the class that it is testing. We just compile and run a class to execute its tests.
  • We will create an instance of the class in its main method.
  • Since we are testing inside the class, we technically have access to all private fields/methods in this objec.t
  • We can easily set up cases by manipulating the private data, then test the methods as needed.
  • We should avoid this practice – more sophisticated testing tools will lose access to private data/methods.
  • We should only print output when a test case fails.

9 – Collections

Efficiency
  • When we have many objects to store, we need a way to store them efficiently
  • Efficiency depends on how we are going to use the objects
  • Choosing the right collection for your algorithm can make a big difference in efficiency.
Data Structures in Java
  • Array
    • A single block of memory
    • Contains a fixed number of values
    • Values accessed by integer index
    • All values of the same type
    • Primitive or Reference types
    • A value can appear more than once
    • Not part of Java Collections Framework
  • LinkedList
    • A sequence of values
    • Values accessed in order
    • All of the same type
    • Reference types only
    • Exactly as much space as needed

  • ArrayList
    • Memory space to contain some values
    • Values accessed by integer index
    • The space can grow or shrink as needed
    • All of the same type
    • Reference types only!
    • A value can appear more than once
    • Basically a Python list (mostly)
    • Methods: add, get, remove, clear, isEmpty, size, etc
  • TreeMap
  • HashMap
  • TreeSet
  • HashSet
Efficiency
  • Efficiency for Arrays and ArrayLists:
Indexing by integer index: O(n)

Linear search to find a value: O(n)

ArrayList add().remove()

Requires copying in worst case many values

O(n) unless adding/removing from the end

Maps

  • A map stores key-value pairs
  • The collection is organized by key
  • Use the key to access the value
  • In Python, maps are called dictionaries
  • Java has two types of maps:
    • HashMap – array like
    • Tree Map – tree-like
Aside: Hash Tables
  • Consider student numbers, an 8-digit number
  • We could use the SN as an index to a large array
    • 8-digit index implies an array of size 10^9
    • Actual # of students: 10^5
    • A huge array is a colossal waste of space
  • Better idea:
    • Create an array of roughly the correct size: 10^5
    • Use a function to convert SN to an index for this array
    • Overly simple example: f(sn) = sn%10^5
    • If two SN map to the same index, have a strategy to try somewhere else (beyond the scope of 270)
Using Hash Maps
  • Every Object has a built-in hash function that is functional, but not optimal
  • In a custom class, you can override the inherited hashCode method to create a better implementation
  • Often, you will need to also override the .equals method to be compatible with hashCode
  • Beyond the scope of 270, this topic will be revisited in 280
Tree Concept
  • TreeMaps are stored using a Red-Black Tree data structure
  • Details of this are beyond the scope of the course
  • If you are using objects instantiated from a custom class as the key, your custom class needs to implement the Comparable interface
  • Similarly, if you are storing objects from a custom class in a TreeSet
Sets
  • A set is an unordered collection
  • Operations to store, remove, and check is a value is in the set
  • A set is like a map that only stores keys
  • Just like maps, there are 2 types, HashSet and TreeSet
Steps on Choosing a Collection
  • Determine how you access values
    • Values accessed by integer position: use ArrayList
      • Go to step2, then stop
    • Values accessed by a key that is not part of the object: use a Map
    • It doesn't matter. Values are always accessed in bulk, by traversing the collection and doing something with the value
  • Determine the element types or key/value types
    • For a List or Set, a single type
    • For a Map, the key type and the value type
  • Determine whether element or key order matters
    • Elements or keys must be sorted: Use a TreeSet or Tree Map. Go to Step 6.
    • Elements must be in the same order in which they were inserted: Choice narrowed down to a LinkedList or an ArrayList
    • It doesn't matter: If you chose a map in Step1, use a HashMap and go to step 5.
  • Determine which operations need to be fast
    • Finding elements must be fast: Use a HashSet and go to Step 5
    • Adding and removing elements at the beginning or the middle must be fast: Use a LinkedList
    • You only insert at the end, or you collect so few elements that you aren't concerned about speed: Use an ArrayList
  • For Hash Sets/Maps, decide if you need to implement .equals() and .hashCode() methods *
    • If your elements do not support them, you must implement them yourself
  • If you use a tree, decide whether to implement the Comparable interface*
    • Decide whether to supply a comparator.
Primitive Data Types
  • You may notice that all Collections (except Arrays) can only store reference data types
Wrappers and Auto-boxing
  • Java provides wrapper classes for all primitive datatypes
  • Primitive values can be wrapped or boxed for use in Collection classes
    • E.g. ArrayList<Integer> numbers = new ArrayList<Integer>()
  • Java will automatically box and unbox between the primitive and reference version of the data
    • E.g. You can insert a variable of type int and Java will automatically convert it to type Integer before inserting it
Why Primitives and Wrappers
  • Unboxed primitive values are very efficient
    • Values stored in local memory
    • One step to work with any primitive value
    • Arrays are very compact
  • Wrapper classes are reference types
    • Values stored on the heap
    • Two steps to work with the wrapped values
    • ArrayLists less compact

10 – Generics

ArrayList as a Container
  • ArrayList is a Container class
  • An ArrayList can hold any type of data
  • The type of data is determined at runtime, when the ArrayList is declared
  • The ArrayList class is written in a generic way (I.e., it knows it will contain some data, but doesn't need to know the specific type)
  • We can define the same behaviour in our classes too
Restricting Generic Type
  • Sometimes we want the flexibility of generic typing, but implementation details require a restriction on the types of data accepted
  • E.g., our previous Zoo example required all monsters to be able to receive damage by implementing the Damageable interface
  • We can restrict the type, I, to a specific type using the extends keyword (for both class and interface types)
Comparing Generic Types
  • Our Stack can hold any type of data, which means using > or < does not work
  • We need a way to guarantee our generic type is always able to be compared to other instances of its own type
  • We will use Java's Comparable interface
Comparable Interface
  • If a class you are creating requires a comparison between instances of that class (e.g., Sort Students in alphabetical order, determine which InventoryItem is the most valuable, etc) that class should Implement the Comparable Interface
  • Requires you to implement the method int compareTo(T other) which returns an integer indicating an object's comparison to another instance (<0 if less, >0 if greater, ==0 if equal)

11 – Exceptions

Exception
  • An exception is any event that disrupts the normal flow of the program's instructions
    • Expression with divide by zero
    • Methods called with invalid arguments
    • User enters bad data
    • File cannot be opened
  • Java Exceptions are objects
    • Created when the even is detected
    • Passed to the JVM
    • Normal execution of code is halted
What happens in an exception?
  • The JVM takes the object and checks if it can be handled
  • If the program does handle it, normal execution restarts where it was handled
  • If the program doesn't handle it, the application halts, and an error report is displayed
Exceptions Replace Error Codes
  • In older languages, programmers used informal return codes to indicate an error
    • E.g., -1 if argument out of range, -2 if file not found, etc.
  • Problem: programmers could (and often did) simply ignore them
Two Ways to use Exceptions
  • To detect and handle exceptions that can be managed by a running application.
    • Bad data, file not found, etc.
    • These are not the programmers' fault
    • Solution: try to recover, ask again, etc.
  • To signal errors in the code that need to be debugged and fixed.
    • Divide by zero, invalid use of methods, etc.
    • These are the programmers' fault
    • Solution: fix the bug

Catching Exceptions

  • An exception is created then passed to the JVM
  • The JVM looks if any running method knows what to do:
    • main() calls A()
    • A() calls B()
    • B() calls C()
    • C() throws an exception
  • JVM will check if B() can handle it, if not then A(), if not t hen main(), if not JVM halts the program with an error.
  • Which method should handle an exception? (A, B, C, or main)
  • The method that has enough info to do it right
  • A method can handle some kinds of exceptions, but not others
  • All other exceptions are automatically passed on.

Types of Exceptions

  • Throw/catch applies to three types of exceptions.
  • Error: Internal JVM errors, not considered her
  • Unchecked: Runtime Exceptions
    • Caused by the programmer's bad code
    • Compiler does not force you to handle them
  • Checked: All other exceptions
    • Not the programmer's fault
    • Compiler checks to make sure you handle these
    • Things like IOException, FileNotFoundException, etc.
The throws Clause
  • Recall that checked exceptions must be explicitly caught and handled
  • If you write a method that could potentially throw a checked exception you must declare that as a part of the method signature.
  • If you method catches the exception, the throws clause is not required.
The finally Clause
  • finally is an optional clause in a try/catch block
  • Used when you need to take some action regardless of whether an exception is thrown/caught
  • Throw early:
    • When a method detects a problem that it cannot solve, it is better to throw an exception rather try to come up with an imperfect fix
  • Catch late:
    • Conversely, a method should only catch an exception if it can really remedy the situation
    • Otherwise, the best remedy is simply to have the exception propagate to its caller, allowing it to be caught by a competent handler
  • Do not squelch exceptions:
    • When you call a method that throws a checked exception and you haven't specified a handler, the compiler complains
    • It is tempting to write a "do-nothing" catch block to "squelch" the compiler and come back to the code later. Bad idea!
    • Exceptions were designed to transmit problem reports to a competent handler
    • Installing an incompetent handler simply hides an error condition that could be serious

14 – Design Patterns

  • A class should represent a single concept.
  • A class is cohesive if all of its methods and attributes are related to the concept that the class represents.
    • High cohesion: everything in a class is closely related to the purpose
    • Low cohesion: lots of mixing of concepts
Coupling
  • A UML diagram indicates which classes use methods from other classes
    • If many classes have relationships to each other, the coupling is high
  • Low coupling is preferred.
  • You can think of this like reducing friction between individual components in a machine
  • Some friction is necessary, but too much makes the machine operate sub-optimally
  • High coupling correlated with low cohesion, problematic
  • High cohesion correlated with low coupling, ideal
Software Design Patterns
  • A design pattern is:
    • A way to structure some part of your application code
    • A general approach to common design problems
    • Based on experience, not rules
  • Design patterns are techniques to apply to:
    • Reduce coupling
    • Increase cohesion
  • Pattern consists of:
    • Intent of the pattern, briefly describing the problem and the solution
    • Motivation further explains the problem and the solution the pattern makes possible
    • Structure of classes shows each part of the pattern and how they are related
    • Code example in one of the popular programming languages makes it easier to grasp the idea behind the pattern
  • Patterns are different from algorithms. An algorithm is like a cooking recipe with exact steps while a pattern is like a blueprint without exact order of implementation.
Types of Design Patterns
  • Creational - Focus on object creations
    • e.g., Singleton, Factory
  • Structural - Focus on organizing different classes and objects to form larger structures and provide new functionality
    • e.g., Adapter, facade
  • Behavioural - Focus on common communication patterns between objects
    • e.g., Command, Strategy

15 – Singleton Design Pattern

Singleton Pattern
  • Does two things:
    • Guarantees that only one instance of a class can exist in a system
    • Provides global access to that instance from anywhere in the system
How to Use Singleton Pattern
  • Create a class to store the object/data you want to apply the pattern to
  • Do not let it create more than one instance of that data
  • Do not let any other class call the constructor
  • All interaction with the single instance uses static methods
Static Attributes and Methods
  • In Java, we can create static methods and attributes using the keyword static
  • Static Attributes:
    • A single value shared by all instances
    • Contrast: object attribute values are not shared
  • Static Method
    • Used by providing the class name, not an instance/objects
    • Can only use static attributes and local variables
    • Cannot use instance attributes
Singleton Structure

Singleton Recipe

  • A singleton class can have only one object (an instance of the class) at a time
  • To design a singleton class:
    • Make the constructor private
    • Use a private static attribute to store the object
    • Write a static method that returns this object

16 – Factory Pattern

Motivation
  • In a large system, it can be dangerous to write code that explicitly references a specific class
  • In many cases we want to program to the supertype (i.e., store and reference objects as their superclass or interface types)
  • Allows more flexibility if the subclasses need to change a little bit, it doesn't break all of our code because we are almost never referencing those subclasses explicitly
  • The one exception is object creation. If we want a Starfishy, we need to explicitly create an object of type Starfishy before storing it as type Monster.
Factory Design Pattern
  • The Factory Pattern is a way of abstracting the object creation process to reduce coupling between specific classes and other parts of our system
  • Instead of explicitly creating something of type Starfishy, we specify that we would like a Starfishy, but the factory gives us something of type Monster.
Limitation
  • Our MonsterFactory uses String as the parameter type
  • This leaves lots of room for typos.
  • Java has a feature called enum (or enumerations) that allow us to create a more robust version of this
Java Enums
  • An enum is a type of Java class that represents a named group of constants
  • Effectively, they are integers but the range is restricted to a specific set of names
  • The programmer can use written words, the computer treats them as numbers, and the compiler prevents you from using a labelw that isn't part of the specified set.

17 – Strategy Pattern

Design Principle 1
  • Identify the aspects of your application that vary and separate them from what stays the same
    • Create new classes for these behaviours
Design Principle 2
  • Program to a supertype, not an implementation
    • Use a supertype to represent each behaviour
      • Each implementation of a behaviour will implement one of these supertypes
      • Can be an interface, abstract class, or a class. The main point is that it should be the most general type it can be.
Design Principle 3
  • Favour composition (has-a) relationships over inheritance (is-a)
    • Each sub-class of Duck:
      • is-a Duck; inherits swim()
      • has-a FlyBehaviour
      • has-a QuackBehaviour
Strategy Design Pattern
  • Defines a family of algorithms
  • Encapsulates each algorithm
  • Makes them interchangeable
  • Lets the algorithm vary independently from the clients that use it

18 – Three Layer Architecture

Architecture vs Design
  • Design Patterns are best practices for specific pieces of a software system
    • e.g., The factory pattern allows us to abstract the creation process of an object
  • Software Architecture refers to the organization of the system as a whole
  • Less concerned with specific details, more concerned with the overall structure of your system
Three-Layer Architecture
  • Presentation layer
    • User interface
    • Call methods in the Domain layer
  • Domain layer (or business layer)
    • The methods called by the Presentation layer
    • Gets the work done
  • System layer (or data layer)
    • The collections (databases) needed by the domain layer
    • Often another language or technology (e.g., SQL, Python, etc)
Advantages
  • Reduces coupling
    • Layer only calls methods in the layer below
    • Within a layer, limit coupling
  • Increases cohesion
    • Each layer's classes can be focused on smaller tasks
  • Organization
    • Useful design decomposition for many large programs
    • Especially for programs focused on more "businessy" applications (e.g., banking application, hotel reservation, etc.)
Layer Separation
  • How do we seprate the Presentation and Domain layers?
  • The Command Pattern
    • Encapsulates each request as an object
    • Requests can be collected, sent as arguments to methods, etc
    • At an appropriate time, the request can be executed.

19 – Command Design Pattern

Command Pattern
  • Encapsulates a single request as a Command object
    • A request can be any method for an action or task performed by an application
  • Command objects
    • Hide the action behind a common interface
    • Perform their action independently
    • Can be tested automatically
  • Similar to the Strategy pattern, the command pattern uses composition
Command Interface
  • Define a Command interface similar to the Strategy pattern
  • Create a new class for each unique request and implement the command interface
  • Write the code for that request in the method defined in the interface
  • Create a new object for each request as needed
  • Can store requests in data structures, pass them around to methods, etc
  • Essentially, we are taking a verb (action) and treating it as a noun (thing)
Strategy vs Command Pattern
  • Both patterns take operations out of the original class that contained them
  • Put them into another object to provide for independent variability
  • The differences are in the use cases encountered in practice and the intent behind each pattern
  • The command pattern makes an object of what needs to be done
  • Stores a command for later use
  • There will need to be a large number of distinct command objects that pass through a give point in a system over time
  • The command objects will hold varying parameters describing the operation requested
  • The Strategy pattern, on the other hand, is used to specify how something should be done
  • Plugs into a larger object or method to provide a specific algorithm e.g. A strategy for sorting might be a merge sort, insertion sort ,or perhaps something more complex like only using merge sort if the list is larger than some minimum size
Summary
  • A request wrapped under an object as a command
  • The command object is used by an invoker object
  • A client class then uses the invoker object to uniformly execute all of the commands for various kinds of requests

20 – Observer Design Pattern

Observer Pattern
  • The observer pattern defines a one-to-many dependency between objects so that when one object changes state, all its dependents are notified and updated automatically
  • Three elements in the Observer Pattern:
    • Subject or Observable
    • Observer
    • Client/driver program
How to Minimize Coupling
  • The subject should not know everything about the observer
  • The observer should not know everything about the subject
  • The subject needs to be notify the observer that the data has changed, but it should not know the details of who it is notifying
  • Usually, if an object a of type A can invoke a method in another object, b of type B, a can invoke an visible method of b. This can make it difficult to modify class B without needing to modify class A.
  • Also, type A needs to know of the existence of type B.
  • If A only needs method m() of B, how can this strong coupling be reduced?
    • Define an interface, T, with the features of B needed by A.
    • Alternate notation: ball-and-socket notation. The ball end is called a lollipop
Example: JButton
  • The class JButton has the method:
    • Public void addActionListener(ActionListener a1)
  • ActionListener is an interface
  • Class JButton is part of the Java API, so it certainly does not know anything about a listener that you write, except that it implements the ActionListener interface.
Observer Design Pattern

Advantages

  • Provides a loosely coupled design between objects that interact. Loosely coupled objects are flexible with changing requirements. Here, loose coupling means that the interacting objects should have less information about each other.
    • Subject only knows that an observer implements the Observer interface, nothing more
    • There is no need to modify the Subject to add or remove observers
    • We can reuse subject and observer classes independently of each other

21 – Model View Controller Architecture

Model-View-Controller Design Pattern
  • Model:
    • stores data and performs business logic to do tasks
    • Notifies the View when its data changes
  • View:
    • Takes user input
    • Presents and visualizes data
  • Controller:
    • Receives user input
    • Converts user input into messages to the model
MVC - Interaction Cycle
  • MVC matches with the interaction cycle; the way humans interact with an interactive application
Benefits
  • Provides recognizable structure to your application
  • Offers separation of concerns that promotes code reusability
Adoption
  • MVC is a very popular software architecture
  • Originally introduced in SmallTalk in the '70s, and it is language- and platform-agnostic
  • Commonly used for developing user interfaces that divide the related program logic into three interconnected elements
  • Popular for designing games and visually interactive systems (e.g., drawing application)
MVC with Observer Pattern

View - Observer

  • Implements the Observer interface
  • The update() method is called by the Model when its data has changed
  • How does a model tell the view that its data has changed?
Model - Observable
  • Make the model inherit from the Observable class in Java
  • This allows the model to have an Observer added to it
    • addObserver(Observer o) is a method inherited from Observable class
    • model.addObserver(view) can be placed somewhere (usually right after model and view are created) to let the view be notified when the model wants
In the Model
  • In the model, after making a change to the data:
    • Call setChanged() to indicate the data has been changed
    • Call notifyObservers() to notify all observers that the model has changed
    • This causes their update() method to run
Updating the View
  • Once the view has been notified that a change has been made, it can either:
    • Request for the data from the model (pull) via accessor methods
    • Or can be sent some data directly (push)
  • If pull is used, the view needs access to the model (stores the model as an instance variable)
Push Updates
  • To get push updates when the model changes, use a different version of notifyObservers():
    • notifyObservers(Object arg)
  • This sends an object of your choice to all Observers
  • If push is used, the view doesn't necessarily need direct access to the model
Observers
  • There can be more than one observer for a model
  • They all get notified when the model changes and issues a notification
  • Notice that the model knows little about the observers
  • This promotes reuse and reduces coupling
Controller
  • The controller is still doing a lot of work
  • If the user is interacting, it is the controller that is responding
  • If a button is clicked, the controller intercepts and tells the model to change
  • This causes observers, such as the view, to be notified
  • Then the view either receives data from the model, or asks for the data from the model.
Summary
  • MVC architecture is commonly used to design interactive systems
  • The Observer pattern can be used to facilitate the updates between the Model and View

25 – Multithreading

Single Thread Application
  • Until now, all of our programs and scripts have had a single 'thread'
  • A thread is a single trace of the execution path for a single program
  • A multi-tasking operating system can execute multiple applications concurrently, by allowing each application to run for a short time in a round-robin sequence
Resource Usage

Multithreading

  • Multithreading allows concurrent execution of two (or more!) parts of a single program
  • Threads are 'light-weight'
  • Not every language has the ability to use threads
Processes vs Threads
  • When an application is executed, the OS creates a 'process'
  • Includes information needed by the app, (e.g. , memory) and for the OS to monitor the app
  • Modern OS can run multiple processes at the same time, each process can have multiple threads
  • A thread is executed inside the process (i.e., has access to the same shared memory and resources)
Reasons for Multithreading
  • Improve performance of the application - break big jobs into independent pieces
  • Improve user experience - separate threads for UI and 'work'
  • Improve software design - break complex sequential code into independent tasks
Improving Performance
  • Multithreading can lead to a speed up of your application
    • Divide a large job into multiple independent threads
    • Run all the threads at the same time
  • Speed-up depends on true concurrency
    • Multi-core processors make this possible
  • Speed-up depends on the job being done
Improving User Experience
  • Single-thread applications force users to wait while work is done
    • Fine if the work is fast
  • Multithreading can separate the UI from the work
    • e.g., Load a second web-page on a new time while scrolling through the first
    • e.g., Load in a new area in a video game while walking towards it
Improve Software Design
  • Break a sequential task into 2 independent concurrent tasks
  • E.g., network application
    • One thread listens for service requests
    • Other thread(s) perform requested service(s)
Thread Objects
  • Key methods:
    • void run(): the task to be performed
    • void start(): start the thread, JVM calls run()
    • wait(): thread waits for a signal
    • sleep(long ms): thread sleeps for a time
Two Ways to Create Threads in Java
  • With inheritance
    • Extending the Thread class
    • Override the run() method
  • Using Runnable Interface
    • Implement the run() method
    • Create a Thread for the Runnable object
Problem: Shared Access
  • What happens when two (or more) threads all want access to the same shared resource?
  • E.g., Multiple threads trying to write to the same file
  • E.g., Deposits and Withdrawals happening to the same bank account
  • E.g., Processing a large amount of data with multiple threads
Race Conditions
  • Race Condition:
    • The effect of multiple threads on a shared resource depends on the order in which they are scheduled
  • Atomic Actions:
    • An action that cannot be interrupted until it is complete
  • Atomic actions are at the machine code level, not the Java source code level
    • E.g., addition is atomic: balance + amount
    • E.g., a complex assignment statement is not atomic when compiled to multiple JVM machine instructions: balance = balance + amount;
Handling Race Conditions
  • Allow only one thread to access the resource at a time. Once it finishes, the other(s) can have access
  • This is called synchronizing
  • Access is controlled by having a lock
    • When one thread has the lock for a resource, no other thread can access the resource until the thread holding the lock has released the lock
  • Java has 2 independent ways to handle locks
    • Special lock objects
    • A built-in lock in every object
Using built-in locks
  • Place the synchronized modifier on a method
    • Only allow one thread to use the method at a time
public synchronized void myMethod() {}
  • There are other similar uses for the synchronized keyword
Using specialized lock objects
  • Lock object: used to control threads that manipulate shared resources
  • In Java: Lock interface, and several classes that implement it
    • ReentrantLock: most commonly used lock class
  • Typically, a Lock object is added to a class whose methods access shared resources
Lock Object Methods
  • lock():
    • Try to obtain the lock
    • If successful, other threads cannot obtain it
    • If unsuccessful, the thread is paused
  • unlock():
    • Release the lock
    • Now other threads can try to obtain it
Synchronizing Object Access
  • Code that manipulates shared resource is surrounded by calls to lock and unlock
balanceChangeLock.lock();

// manipulate the shared resource

balanceChangeLock.unlock();

  • What happens if the code between lock and unlock throws an exception?
Synchronizing Object Access - Exceptions
  • Wrap the code between lock and unlock in a try block, and place the call to unlock in a finally statement
  • If an exception is thrown, the lock will be released so another thread can use it
  • If this isn't done, the program will be stuck
balanceChangeLock.lock();

try {

//manipulate the shared resource

}

finally {

balanceChangeLock.unlock();

}

Second Problem

  • Consider a scenario:
    • Thread 1 acquires a lock for Object A
    • Thread 2 acquires a lock for Object B
    • Thread 1 needs to manipulate object B before it can return the lock on A
    • Thread 2 needs to manipulate object A before it can return the lock on B
  • What is the problem here?
Deadlock
  • A deadlock occurs if no thread can proceed because each thread is waiting for another to do some work first
  • It is the developer's responsibility to prevent deadlock
  • How can we solve this?
Condition Object
  • To overcome this problem, use a condition object
  • Condition objects allow a thread to temporarily release a lock, and regain the lock at a later time
  • Each condition object belongs to a specific lock object
  • You obtain a condition object with newCondition method of the Lock interface
  • You need to implement an appropriate test (boolean expression). As long as the test is not fulfilled, call await on the condition object
Condition Objects - await()
  • Calling await:
    • Makes the current thread wait
    • Allows another thread to acquire the lock object
  • To unblock, another thread must execute signalAll on the same condition object: sufficientFundsCondition.signalAll();
  • signalAll unblocks all the threads waiting on the condition
  • signal randomly picks just one thread waiting on the object and unblocks it
  • signal can be more efficient, but you need to know that every waiting thread can proceed
  • Recommendation: always call signalAll
Summary
  • Multithreading can make your code faster, more efficient
  • Race Conditions and Deadlocking are issues that may arise
  • Locks can prevent race conditions but cause deadlock
  • Condition objects can resolve situations of deadlock
