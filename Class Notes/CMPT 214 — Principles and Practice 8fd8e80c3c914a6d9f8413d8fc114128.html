  • Distinguish between interpreted languages and compiled languages
    • We call languages like C and Python high-level languages (HLL) meaning that they are at a higher level of abstraction than machine code that can be directly executed, and human readable. For any HLL to run on a computer, the code must first be translated into machine code that can be directly executed on the CPU. This translation is either performed by interpretation or compilation. Usually only one type of translation is used for a particular HLL.
    • An HLL that uses interpretation to translate to machine code is called an interpreted language. The program that performs the interpretation is called an interpreter. Interpretation is used to translate HLL programs to machine code only when they are run, and only as needed, one line at a time.
    • An HLL that uses compilation to translate to machine code is called a compiled language. The program that performs the compilation is called a compiler. A compiler translates the entirety of a program to machine code all at once and a program must be thusly translated before it can be run. C is an example of a compiled language.

6 – Storage Allocation

  • define and distinguish between automatic, static, and dynamic allocation of storage (i.e. variables, memory); and
    • At some point in the execution of a program, specific memory addresses have to be associated with specific variables so that the values of variables can be stored there. This process is called storage allocation or memory allocation. In other words, storage allocation is the assignment of specific memory locations to specific variables.
    • In C there are three different methods of storage allocation. They are distinguished by when the allocation happens, and where the memory is allocated
      • Stack – The stack is the same stack where we find the stack frames of function calls. It should therefore not surprise you that local variables and function parameters are stored here since, as we know, those variables are stored in stack frames. As we mentioned before, the stack grows from higher to lower memory addresses and is usually quite limited in size
        • Stack sizes are small for a number of reasons, including that in multithreaded processes, stack space is shared by all threads, and that it is rare for a process to legitimately need a larger stack, so a small stack conserves memory in modern systems where hundreds or thousands of processes may be running.
        • You can view the size (in bytes) of the process stack on your system using the terminal command ulimit -s.
      • Heap – The heap is the pool of memory from which programmers may explicitly allocate memory at runtime. It grows from smaller addresses to larger addresses and is much larger than the stack. It is normally limited only by the amount of system memory available. Storage that is allocated using the dynamic allocation method is allocated from the heap space.
      • uninit.data, init.data – Statically allocated storage lives in these memory areas.
        • The init.data memory space stores statically allocated variables that are initialized in the program code. They are loaded from disk when the program is loaded into memory for the first time by the UNIX operating system’s exec() system call.
        • The uninit.data memory space (also referred to as BSS segment, or Block Started by Symbol segment, a historical anachronism) stores statically allocated variables that are not initialized by the program. Uninitialized variables initialized by the exec() system call when the program is loaded into memory have a value of zero.
        • A program’s global variables are all statically allocated and stored in init.data if they are initialized when defined, or in uninit.data if they are not initialized. Non-global variables can be defined to use static allocation as well
  • understand when and how variables are initialized for different types of storage allocation.

9 – Dynamic Memory Allocation in C

    • It should be pretty obvious how dynamic memory allocation differs from static allocation — static allocation happens at compile-time, while dynamic memory allocation happens at runtime.
    • Dynamic allocation differs from automatic allocation in that the allocation occurs from the heap instead of the stack, and that it requires use of specific library function calls to allocate and de-allocate (free) the memory space.

13 – Multiple File Development in C

  • describe what a module is
    • Separating code into different source files is one aspect of the organization of large software projects into manageable pieces. Typically, a single source code file will store a set of related functions or objects. When used in this fashion, a source code file is often called a module.
    • Modules also provide a layer of abstraction — the outside world knows what a module can do, and uses the module to do it, but it doesn’t need to know how the module does it. In other words, the module encapsulates the internal implementation details of the module.
    • The modules of a C program must be combined at compile time and the compiled code for all of the modules of a program are stored together in one single executable file.
  • describe the phases of building an executable program from a single source file, the input to each phase, what happens during each phase, and what each phase produces as output
    • There are four phases that a source file must pass through before it becomes an executable program:
      • C preprocessor: Gets a module ready to be compiled; outputs .i file
        • Execute preprocessor directives, start with # character.
        • Substitute macro names
        • Remove comments
        • C preprocessor also adds some additional information into the file called line markers that are used for a variety of purposes including producing compiler error messages. When a compiler error occurs, the most recently encountered linemarker is used to indicate where in the source code the error occurred. Because of the linemarkers, the output of the C preprocessor is technically no longer a C source file. It is now a .i file. After preprocessing, the modified module, that is, the resulting .i file, is passed on to the compiler.
      • Compiler: Compiles modules into assembly code; outputs a .s file
        • The C compiler performs the translation of a preprocessed .c file (that is, a .i file) into assembly language code.
          • Assembly language code is a “human readable” version of machine code, where individual CPU instructions have names (rather than unreadable numeric codes).
          • The compiler performs many code optimizations at this stage to produce more efficient assembly language code than might result from direct literal translation from C to assembler.
      • Assembler: Translates (or assembles) assembly code output from the compiler into machine code; outputs a .o file
        • the compiler calls on the assembler to translate the resulting assembly code into machine code. The result of the assembler process is an object file with a .o extension.
        • The object file contains (among other things) the compiled and assembled machine code, and a symbol table which records the names of certain variables and their locations within the object file for use by the linker. The symbol table is important when compiling multiple files together into a single program. For example, it allows the linker to match up a function call in one .c file to the actual function definition in another .c file.
      • Linker: Combines all of the modules of a program, and any libraries it uses into a single executable file.
        • The linker combines one or more object files, the standard C library, and any other libraries that might be requested into an executable program.
        • Object files do not contain any knowledge about what other .o files may be combined with them or their contents. They contain placeholder memory addresses for functions and variables that are used in the module they were compiled from but defined in another module or library (such as library functions, e.g. printf(), scanf(), etc.). Thus, one of the jobs of the linker is to reconcile these temporary memory addresses within individual modules and to combine all of the .o files and libraries together into a single address space where each reference to a function/variable in the various modules refers to the same correct memory address in the module where it is actually defined.
        • This is called resolving symbols. Symbols (variable and function names) used in one file but defined in another must be resolved to refer to their actual addresses in the file in which they are defined. This can only be done at link-time because the preprocessing, compiling, and assembling of each module is done independently without looking at any other modules.
        • Symbol resolution happens during the linker phase.
        • It means matching function and variable names used in one file with their actual definitions in other files or libraries.

    • The inter-module scope of a non-static global variable is: All modules in the program.
    • The inter-module scope of a static global variable is: The module it is defined in only.

16 – Version Control

  • describe the purpose and benefits of version control
    • Version control systems help software developers keep track of their updates to the code of a software system under development.
    • Every change that is made to the code can be tracked and attributed to the person who made the change.
    • Separate independent threads of development can be created and merged later when desired.
    • Versions of the code that have been released to customers can be traced and retrieved.
  • describe at least three models of version control
    • File sharing - There is a single version of the code on a central server that can be downloaded by anyone. When a developer changes a file, they upload the changed file. You inform other people on your team of which file(s) you are working on and they respect your notification and don't change code that others are working on.
      • Not really a version control system at all. just an agreement between software devs to behave nicely.
      • High risk of people forgetting to respect who is working on what
      • High risk of having changes lost or overwritten by other people's uploads
      • Does not retain previous versions of the software project, maintaining only the current version
    • Lock-modify-unlock - When someone wants to work on a specific file from the centralized version of the project, they are required to check out the file, and the server records a lock on the file, preventing others from checking out the same file. When the person who checked out a file is finished making modifications, they upload the changed file and the lock is released. The previous version of the file is also retained. All developers can read the contents of a locked file but cannot modify it.
      • Ensures that there is no possibility of changes being lost by overwriting.
      • Also means that there cannot be more than one person working on a file at the same time.
      • There is the problem that someone might forget to release a lock, preventing another dev from doing their work.
    • Copy-modify-merge - Many programmers can check out a copy of a file from a central repository. Each can then make changes. When a programmer uploads a modified file to the repository, the system checks to see if anyone else has uploaded a modification of the file since that programmer first checked it out. If so, the programmer gets an "out of date" error. They have to download the modified file from the central repository, and manually merge their own changes into the "up to date" copy from the sever, then upload the merged copy.
      • Advantage of not requiring locks, which allows multiple programmers to work on the same file
      • Avoids the danger of someone forgetting to remove the lock
      • On the other hand, merging is still a process that might have to be done manually if two people update the same lines of the same file
      • Otherwise, merging can be done automatically
    • Distributed model - where there need not be a centralized repository that contains the authoritative copy of the software project. Each developer can have their own copy of the repository. Each of their copies contains a complete history of all changes to the project that they know about. Developers can share changes with others via public repositories. Merging of changes to the same file happen automatically in most cases.
      • Can be set up in a number of configurations.
      • Git uses the distributed model.

18 – Shell I/O Redirection

  • name the standard I/O streams, and their default sources of and destinations for data
    • All running programs in LINUX have three standard input and output data streams. They are called stdin (short for standard input), stdout (standard output), and stderr (standard error).
      • stdin: an input data stream that programs can read data from.
        • Default data source for stdin is the terminal (text entered at the keyboard)
        • It is possible to use special BASH shell syntax to change the data source of stdin to come from somewhere else, such as a file.
      • stdout: an output data stream that programs can write data to.
        • Default data destination for stdout is the terminal.
      • stderr: an output data stream that programs can write data to.
        • Default destination for stderr is the terminal.
    • It is the programmer that is responsible for defining the expected syntax and semantics of the data that a command reads and writes to/from the streams.
  • explain why the LINUX operating system provides standard I/O streams to every program
    • The idea in LINUX is that the operating system provides every program with these streams. Programs can then utilize these streams as their default sources of input data and destinations for output data.
    • When commands use these streams for input and output, they become much more versatile because we can change where that input comes from and where that output goes at the level of the shell, without having to modify the source code for the command and recompile it!.
    • Thus standard I/O streams are an abstraction of input and output that can be utilized by commands and manipulated by the shell to achieve more versatile and customizable behaviour from commands.
  • explain why there are two different standard streams for output and their intended usages
    • The reasons is so that we can separate actual program output from diagnostic messages such as errors or warnings.
    • For example, we might want to redirect a command's stdout to a file, but we might still want to see any warnings or errors appear on the terminal. If both types of output went to the same output stream, both would be redirected to the same place.
  • describe the difference between the default I/O streams utilized by a command and the default sources and destinations for the standard I/O streams
    • It is important to understand that there are two sets of “defaults” in this discussion.
    • First, from the shell’s point of view, stdin has a default source (the terminal), stdout and stderr have default destinations (also the terminal). These default sources and destinations can be changed by the shell using redirection operators which we will introduce in the next section.
    • Second, from a program’s point of view, it can default to reading/writing to/from the standard I/O streams or not. The programmer of a LINUX terminal command has choices to make. They can program the command such that it reads from stdin by default or not. They can write the command such that it writes to stdout by default or not. Thus, to say that “the cat command reads from stdin by default” is not at all the same as saying “the default source for stdin is the terminal”. These are independent things. The default behaviour of cat is to read from stdin, but it has no way of knowing whether the default source of data for stdin has been changed by the shell! These two defaults (cat’s use of stdin as it’s default input stream, and the default source of data for stdin) exist at two different levels of abstraction. This is what achieves the versatility and customizability.
  • add shell redirection operators to terminal commands to change the sources and destinations of the standard I/O streams for that command's invocation
    • Redirecting stdin
      • < <path-to-file>
        • stdin is redirected by appending this syntax to the end of a command where <path-to-file> is a pathname specifying a file.
    • Redirecting stdout
      • > <path-to-file>
        • stdout is redirecting by appending this to a command where <path-to-file> is a pathname specifying a file.
        • This causes the file <path-to-file> to be deleted (if it exists).
        • A new empty file is created and any data that the command writes to stdout is written to the file.
        • For example, "ls > file_list.txt" causes any output written to stdout by ls to be sent to the file file_list.txt. Again note that this changes only the destination of stdout. The ls command itself is still writing its output to stdout.
      • >> <path-to-file>
        • Alternatively, you can append this. The difference is that if there is an existing file called <path-to-file>, it is not deleted, and the output of the command is appended to that file after its existing contents.
    • Redirecting stderr
      • It takes more effort to redirect this, we'll return to this later.
    • It is important to note that these syntax elements for redirecting I/O are not command arguments, options, or option arguments. They are additional syntax that is understood by the shell and are not passed to the command as arguments. Think of < and > as I/O redirection operators, and the filenames as operands to those operators.
  • explain what a file descriptor is and name the specific file descriptors associated with the standard I/O streams
    • A file descriptor in the shell is just a number that the operating system assigns to an open I/O stream to or from a file in the filesystem.
      • When any file is opened by the OS, the OS keeps track of which file it is by assigning it a file descriptor.
      • File descriptor of stdin is always 0.
      • File descriptor of stdout is always 1, stderr is always 2
      • If the file descriptor is omitted from the input redirect operator < it is assumed to be 0 (stdin) by default.
    • The full syntax for the redirection operators are:
      • <file-descriptor> < <path-to-file>
      • <file-descriptor> > <path-to-file>
    • If we want to redirect stderr, we need to specify the file descriptor 2 with the output redirect operator, like this:
      • wc -l < file_list.txt 2> error_log.txt
        • This would redirect stdin to come from the file file_list.txt, and redirect stderr to the file error_log.txt.
    • Redirecting stdout and stderr to the same place is a bit trickier. You’d think we could just do this:
wc -l < file_list . txt > file_count . txt 2> file_count . txt

but if we do this, both stdout and stderr can be written to independently, which can cause the output from the two streams to interrupt each other and appear in the file in an unpredictable order, and not the order in which the program actually produced those outputs

20 – LINUX Process Abstraction

  • describe what a process is and basic info about processes that are stored by the kernel
    • A process is an operating-system level entity. You can intuitively think of a process as a program running in the operating system. Unless we take special measures, a process consists of a single thread of execution. Every process in the LINUX operating system has a unique process ID or PID which is an integer.
    • The notion of a process is distinct from that of a program. When we issue a command to run a program, a process is created in the operating system which runs the program. Thus, we can think of a process as an instance of a running program. The operating system could have many processes that are all running the same program.
    • Processes can run other programs, which causes more processes to be created. For this reason, processes in the OS exist in a hierarchy. Each process has a unique parent (the process that crated it). If a process creates new processes, they are called children of that process. Children of the same process are called siblings.
    • This raises the question of what process is at the root of this hierarchy, the short answer is that it is the operating system kernel.
      • When you log in or launch a terminal window, the kernel creates a shell as a child process, and when we enter commands into the shell, the shell creates a child process to run the command we entered. Thus all processes have the kernel as their most distant ancestory process.
  • identify and define common process states
    • A LINUX process has a state. Among other things, the process state can be:
      • Running/runnable: The process is running or is ready to run and is waiting for its turn to use the CPU.
      • Wait: The process is waiting for an event to occur, such as receipt of input from the keyboard, or waiting for a child process to terminate.
      • Suspended: A process whose execution has been paused. A suspende3d process still exists as a process, its state of execution at the time of its suspension is retained and preserved, but it does not continue executing. It can be resumed from the point at which it was suspended.
      • Terminated: A state that briefly exists after a process has ended its execution while the operating system is releasing its resources and removing the process from the system.
      • Zombie: A process that has terminated and is waiting for its termination to be acknowledged by its parent.
  • describe in general terms what signals are and some examples of how they are used
    • The operating system defines a set of signals. Every process is capable of receiving these signals. Signals sent to a process by the operating system interrupt the execution of that process. For each possible signal, a program can define a special handler function that gets called when a process running that program receives that signal.
    • If a program does not define a signal handler for a signal that a process running that program receives, then the operating system imposes default behaviour.
    • One example, one signal is called SIGTERM. The purpose of this signal is to terminate the process that receives it. A program may define a handler for this signal, which gets executed when the signal is received. Usually such a handler is written to clean up what the program is doing (e.g., save an open document) and exit gracefully. If a program doesn't define a handler for SIGTERM, the default behaviour is to immediately terminate the program, even if important tasks are incomplete.
  • list the basic steps that are carried out when the shell executes a command
    • A fairly high-level view of what happens when a user enters a shell command is that:
      • The shell interprets the command.
      • The shell creates a child process and executes the command in the child process.
      • The shell waits for the process' completion.
    • Some shell commands are defined internally within the shell, such as cd and echo. These do not require the creation of a child process. The command is executed entirely by the shell.
  • describe the details of what happens when the shell interprets a command
    • When we first enter a command, the shell receives the entire command as a single string. One of the basic things the shell has to do is separate the command into its command name and all of the arguments to the command.
      • Note that the shell does not distinguish between command arguments, options, and option arguments - this is up to the specific command that is executed (unless the command is built-in)
    • In the absence of any special syntax, all the shell does is separate the command entered into strings separated by spaces which are passed to the child process.
      • In a C program these string arguments are received through the char *argv[] argument to main(). It is then up to the child process' program to examine char *argv[], determine whether they are valid argument, options, or option arguments, and react appropriately.
    • The shell has a lot of syntax that can be added to commands beyond command names, command arguments, options, and option arguments. We have seen some of these, such as I/O redirection, special path characters (such as ~), and file globbing. Other syntax elements that must be recognized are that we have not yet seen are quotations and environment variables.
    • Interpreting a shell command involves the shell parsing the command string, and recognizing these special syntaxes, and taking appropriate actions. Some of these actions, such as actually setting up I/O redirection, cannot take place3 until after the child process is created.
    • Shell command interpretation includes (but is not limited to):
      • pathname substitution
        • The act of substituting actual paths for special path characters such as ., .. and ~
      • file glob expansion
        • The act of replacing file globs (path containing wildcard characters such as * and ?) with the list of files that match the wildcard pattern
      • recognition of I/O redirection operators (but not the actual redirection yet)
        • The process of parsing a command string to find the I/O redirection operators and their operands, and record what standard I/O streams need to be redirected and to/from where.
          • The actual I/O redirection is not done during the process of command interpretation because it cannot take place until the child process for the command has been crated.
      • quotation substitution (chapter 21)
        • The process of replacing quoted strings according to the semantics of the particular quotation. Discussed more in next chapter.
      • environment variable expansion (chapter 22)
        • The act of replacing environment variables in the command string with their values.
        • Environment variables are variables that can be defined within the shell.
  • describe the details of how the shell creates a new process to execute a command
    • Assuming that the command is not a built-in command, a child process must be created to execute the program specified by the command. The shell creates a child process by doing the following:
      • The shell creates a child process by asking the operating system to make a copy of the shell process.
      • The child shell asks the operating system to replace the child process' memory address space with the contents of the program binary. It populates the char *argv[] argument to the main() function of the child process with the space-separated components of the command string, which it identified during shell command interpretation
      • The parent shell process performs the redirection of standard I/O streams for the child process requested by any I/O redirection operators it recognized during shell command interpretation.
      • Execution of the child process begins, and the parent shell process waits until it has run to completion.
    • Steps 1 and 2 are performed by the shell invoking two system calls.
      • System calls are called like any other C function except that they are defined in the operating system kernel rather than a user-level program or library.
        • In step 1, the shell calls the form() system call which creates a copy of the process that calls it.
        • The child process created by fork() completes step 2 by calling the execve() system call which causes the calling process' program to be overwritten by loading the program for the command to be executed into its address space (read from the program's compiled binary). execve() also populates the new process' char *argv[] array with the arguments from the command string read from the terminal (recall that char *argv[] one of the arguments to main() in every C program)
      • For this course, you are not expected to know how to use fork() and execve() in a C program, but you are expecte3d to be aware that these system calls are used together to create a child process and generally what they do, as we have just described it.
        • In step 4, the parent shell process waits for the child process to terminate by calling the wait() system call.
  • list conditions that cause a process to terminate
    • When a process terminates, the operating system kernel releases resources owned by the terminated process and notifies its parent process of its termination.
    • There are a few things that cause a process to terminate normally:
      • When its main() function executes a return statement
      • When execution reaches the end of main() without a return statement
      • When the process calls the exit() function in the C standard library.
    • There are other ways a program can be caused to terminate which result in abnormal termination.
      • One way that a program can be terminated abnormally is if it receives a signal.
        • Example is the SIGTERM signal.
        • Another signal that results in abnormal termination that you very likely encountered in your work with C pointers in this course is the SIGSEGV signal. This signal is sent to a process when it tries to use an invalid memory reference, that is, when it tries to dereference an invalid pointer. The shell recognizes when a program is terminated with SIGSEGV and reports a segmentation fault.
        • Other signals that cause a process to terminate by default ( in the absence of a signal handler for that signal) are SIGBUS (bus error, caused by attempting to use a memory address that does not exist as a physical memory location) and SIGFPE (floating-point error)
  • describe what happens when a process terminates
    • Normal process termination always results in the process calling the exit() system call which releases resources, closes files, and notifies any processes wait()ing for the process to terminate that it has to do so.
  • explain the difference between foreground and background processes
    • When the shell executes a program, its default behaviour as, as previously discussed, is to wait for that program to terminate before accepting any new commands. When the shell executes a process in this way, it is said to be a foreground process.
    • There is an alternative behaviour where the shell can be instructed to run a command as a background process. The shell starts a background process running, but does not call the wait() system call to wait for it to terminate. Instead the shell continues its own execution and continues to accept commands while the background process is running.
    • Since the shell does not wait for a background process to finish, and continues accepting new commands, there needs to be some way for the background process to notify the shell that it has been terminated. When a background process terminates the signal SIGCHLD is sent to its parent process. The shell has a signal handler which gets called upon receipt of the SIGCHLD signal which is defined to perform the necessary tasks to acknowledge that the background process has terminated and notify the user.
