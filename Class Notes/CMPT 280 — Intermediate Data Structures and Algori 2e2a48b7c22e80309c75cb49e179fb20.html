T01 — Lists

  1. List Structure in lib280

    The lib280 library provides implementations of singly-linked and doubly-linked lists.

    Main classes include:

    • LinkedNode280<I>
      • Stores a data item of generic type I
      • Has a reference to the next node

    • BilinkedNode280<I>

    Iterator classes include:

    • LinkedIterator280

    Lists themselves may also contain a cursor.

    Examples:

    • LinkedList280 implements LinearIterator280
    • BilinkedList280 implements BilinearIterator280

    This means the lists themselves can act like iterators.

    So in lib280: lists have cursors and separate iterators also exist.

  1. Cursor vs Iterator

    Cursor:

    • Part of the data structure
    • Used to modify the structure
    • Represents the current position

    Iterator

    • External object
    • Used mainly to traverse data
    • Does not modify the container’s cursor
  1. Important Implementation Detail

    If a method internally moves the cursor but should not affect the user’s cursor position, it must:

    1. save the cursor position
    1. perform operations
    1. restore the cursor
  1. When cursors are hidden

    Some ADTs do not expose a cursor.

    Example: stacks, because the current position is always top, it should not be changed arbitrarily.

    However, stacks could still have iterators for traversal.

T02 — ADT Specification

  1. What a Stack is

    A stack is a container that follows LIFO (Last in, first out)

    The last element added is the first element removed.

    Core operations of a stack:

    • push → add an item to the top
    • pop → remove the top item
    • top → look at the top item
    • isEmpty → check if the stack has no items
    • isFull → check if the stack is full

    Stacks are4 also considered dispensers (structures that determine the current item automatically)

  1. What an ADT Specification contains

    An ADT specification describes a data structure without implementation details.

    It includes five parts:

    • name
    • sets
    • signatures (translate to method headers)
    • preconditions (are javadocs, exceptions, and if-statements)
    • semantics (becomes javadoc comments (and later, code)

T03 — Arrayed Trees

  1. What an Arrayed Binary Tree is

    An arrayed binary tree stores a binary tree inside an array instead of nodes and pointers.

    • Each array index acts like a node.
    • The value stored in the array is the node’s data.
  1. Important Index Rules

    The root is stored at index 1.

    • Index 0 is unused. If we used index 0, the math for children and parents would break.

    If a node is at index :

    RelationshipFormula
    Left child2i
    Right child2i + 1
    Parenti / 2 (integer division)
  1. When Array Trees Work

    Array representation works best when the tree is complete or nearly complete.

    Conditions:

    1. All levels except possibly the last are full.
    1. The last level is filled left to right.

    This ensures array elements are contiguous (no gaps).

    If the tree is sparse, the array would need many empty indices.

    Results:

    • wasted memory
    • inefficient representation

    In these cases, linked-node trees are better.

  1. Inserting into an Arrayed Binary Tree

    Insertion rule:

    • Always insert at the end of the array.
  1. Deleting from an Arrayed Binary Tree

    Deletion steps:

    1. Remove the target element.
    1. Move the last element of the array into the empty position.
    1. Decrease the array size.
  1. Key Advantages vs Disadvantages

    Array trees are:

    • simple structure
    • fast parent/child look up, O(1)
    • good for complete trees
    • used in heaps

    Problems occur when trees are not complete

    • large number of empty array cells
    • wasted memory

T03 — mAry Trees

  1. General trees vs m-ary trees

    A general tree is a tree where each node can have any number of children.

    An mAry tree is a tree where each node can have at most m children.

  1. Implementing mAry Trees

    Each node must store references to its child nodes. There are two common ways.

    1. Method 1 - Array of children

      Each node stores its children in an array.

      Advantages:

      • Fast access to children, O(1)
      • Can access child directly by index

      Disadvantages

      • Maximum number of children must be fixed.
      • Some array entries may be null, which wastes space.
    1. Method 2 - Linked List of Children

      Instead of an array, each node stores a linked list of child nodes.

      Advantages:

      • No limit on number of children.
      • Uses only needed memory.

      Disadvantages:

      • Accessing a specific child requires searching the list, O(n)
  1. mAry Trees in lib280

    The implementation class:

    BasicMAryTree280<I>

    Location: lib280.tree package

    Nodes are: MAryNode280<I>

    Each node contains: array of children.

    So lib280 uses the array method.

  1. Creating an mAry Tree

    BasicMAryTree<String> T = new BasicMAryTree<String>(”Balbo Baggins”, 6)

    Meaning:

    • root item = “Balbo Baggins”
    • each node can have up to 6 children, starting at 1, not 0
  1. Important Methods
    MethodPurpose
    rootItem()Returns the root item
    rootLastNonEmptyChild()Returns the index of the last child that exists
    rootSubtree(i)Returns the i-th subtree of the root
    setRootSubtree(T, i)Sets subtree i.
  1. Traversing an mAry tree

    Traversal is usually recursive.

    Algorithm:

    treeTraverse(node)
print node.item
for each child i
	treeTraverse(child i)

    This visits: node, all children, children of children. This is similar to pre-order traversal.

  1. Implementation Strategy

    Two methods are usually written:

    Public method: starts traversal.

    • Example: traverse()

    Private helper method: handles recursion.

    • Example: traverseNode(node)

    Reason: the user should not interact with internal node structures.

T04 — Heaps

  1. What a Heap is

    A heap is a special kind of array-based binary tree.

    It must satisfy two conditions:

    1. Complete tree property.
      1. Every level is full except possibly the last.
      1. The last level is filled from left to right.

      This is why heaps are stored using arrays.

    1. Heap Property
      1. Every node must be greater than or equal to its children.
      1. So: the largest value is always at the root.

      This type of heap is called a max-heap.

  1. Why Heaps are Useful

    Heaps are useful when you need to quickly access the largest element.

    • Examples: priority queues, scheduling, heap sort
  1. Heap Insertion

    When inserting into a heap:

    1. Insert the element like an arrayed binary tree. Place it in the next open position, bottom level, leftmost
    1. Restore Heap Property
      1. If the new element is larger than its parent, swap them.
      1. Repeat until: element ≤ parent OR element becomes root

      This process is called bubble up.

      Algorithm:

      insert e at bottom
while e > parent
	swap e and parent
  1. Heap Deletion

    Heaps are dispensers. The current item is always the root. So deleting removes: the largest element.

    1. Remove root.
      1. Replace the root with the last element in the heap.
    1. Restore Heap Property.
      1. If the new root is smaller than its children, swap it with the largest child.
      1. Repeat until heap property is restored.

      This process is called bubble down.

      Algorithm:

      move last element to root
while element < largest child
	swap with largest child
  1. Heap as an Array

    Heaps use the arrayed binary tree formulas. See above.

  1. Key Heap Operations
    OperationIdea
    insertadd item then bubble up
    deleteItemremove root then bubble down
    itemreturn root
  1. Time Complexity
    OperationComplexity
    insertO(log n)
    deleteO(log n)
    access maxO(1)

    Reason: heap height: log2(n)

T08 — Kruskal’s Algorithm

Find a Minimum Spanning Tree (MST):

  • connects all nodes
  • no cycles
  • minimum total edge weight

Summary

  • Kruskal’s algorithm is an example of a greedy algorithm. The minimum spanning tree problem is an optimization problem.
  • We’re not just finding a spanning tree, we’re finding the minimum one.
  • A greedy algorithm solves an optimization problem by repeatedly picking the best possible addition to the solution.
  • Each graph edge is a possible addition to the spanning tree.
  • Pick the best one! Then... pick the next best one!
  • Don’t pick any edges that can’t be part of the solution

Implementation Problem

  • In a spanning tree (minimum or otherwise), there can’t be more than one path b/t any two nodes (b/c it’s a tree)
  • We can’t add an edge to the MST that would cause the tree to not be a tree
  • Thus, we need to be able to easily tell when a node is already connected to another node
  • The slow way would be to traverse the current tree starting at one node, and see if we can find the other node using the edges already in the tree, but we can do better than that

Disjoint Sets

  • In general, disjoint sets are subsets of a collection of items where no item can be in more than one subset.
  • Examples; cities can’t be in more than one country.

Implementing Disjoint Sets

  • How do you find out which set an item is in?
  • How do you join two sets t/g?

The find Operation

  • To find which set a node belongs in, walk the directed edges in the graph until you’ve run out of edges (i.e. arrive at the root of a tree)
  • The set that the node is in is represented by returning one node from the set.
  • As long as the find() of two items is the same, then they are in the same set.

The Union Operation

  • To join two sets t/g, you have to add an edge from one set to the other
  • Now find() will find that any item that was in the set of either v1 or v2, will be in the same set.
  • By using find() on the two items, we can make sure that we only ever draw an edge from a node that doesn’t already have a node going out of it.

SELF — File IO

  1. Opening a file

    In Java, files are represented using the java.io.File class. 

    import java.io.File;

File myFile = new File("filename.txt");

    Important:

    • Creating a File object does NOT open the file.
    • It only represents the file path.
  1. Reading Files with Scanner.

    To actually read a file, we use Scanner. 

    import java.io.File;
import java.util.Scanner;

File myFile = new File("filename.txt");
Scanner infile = new Scanner(myFile);

    The Scanner object opens the file for reading.

  1. Handling File Errors

    Opening a file can fail (for example, if the file doesn’t exist) so we use try-catch. This prevents the program from crashing. 

    Scanner infile = null;

try {
	infile = new Scanner(new File("filename.txt"));
}
catch {FileNotFoundException e) {
	System.out.println("Error: file not found.");
	return;
}
  1. Tokens

    When reading files, Scanner reads tokens.

    A token is a sequence of characters separated by delimiters.

    Default delimiter: whitespace

  1. Reading Data
    int sum = 0;

while(infile.hasNextInt()) {
	sum = sum + infile.nextInt();
}

    Important Scanner methods:

    MethodPurpose
    hasNextInt()checks if next token is integer
    nextInt()reads integer
    hasNext()checks if any token exists
    next()reads next token
  1. Closing Files

    After reading a file, you must close it:

    infile.close();

    If you don’t close the file, resources may remain allocated.

  1. Error Checking During Reading

    Sometimes a token may not match the expected type.

    Example problem:

    100
20
hello
30

    Using nextInt() alone would crash.

    Better approach, allows the program to continue reading the file even if errors occur:

    while(infile.hasNext()) {
	try {
		sum += infile.nextInt();
	}
	catch(InputMismatchException e) {
		System.out.println("warning: non-integer token.");
		infile.next();
	}
}
  1. Other useful Scanner methods
    MethodPurpose
    nextLine()read entire line
    hasNextLine()check if another line exists
    nextFloat()read float
    hasNextFloat()check float
    useDelimiter()change token delimiter
  1. Reading Tabular Files

    Example file format:

    Jan 2023 -12.3 4.6
Feb 2023 -9.4 6.8
    1. Method 1 — Token by token
      String month = infile.next();
String year = infile.next();

    1. Method 2 — Read line then split
      String line = infile.nextLine();

  1. Writing Files

    To write files we use BufferedWriter. This opens a file for writing:

    import java.io.FileWriter;
import java.io.BufferedWriter;

BufferedWriter outfile = new BufferedWriter(new FileWriter("filename.txt"));
  1. Writing Data

    Use:

    outfile.write("Hello world");

    Important rules:

    • Only strings can be written.
    • Other types must be converted. 
    outfile.write(Integer.toString(x));
  1. Writing New Lines

    Java does not automatically add new lines. 

    outfile.write("\n");
  1. Closing Output Files

    Always close output files. If you don’t, some data may never be written to disk .

    outfile.close();

6 — Cloning Data Structures

  • define what it means to clone an object
    • Sometimes we want to make a duplicate copy of an instance of an object and the data it contains. This is referred to as cloning.
    • For objects which contain only primitive data, cloning an object is easy: create a new object instance of the same type as the object to be cloned, and copy the instance variables of the original object into the new object.
    • However, if the object to be cloned contains references to other objects, then the process of cloning becomes more involved because we have to ask the very important question: should we clone the objects that are referenced by the object being cloned?
  • differentiate between mutable and immutable objects
    • Immutable data is data that cannot be changed once created.
    • Mutable data can be changed after it is created.
    • In Java, most objects are mutable. Some exceptions are the wrapper classes around primitive data types, such as Integer, Double, Float, and Character — these Java objects are immutable.
  • accurately describe between shallow and deep cloning
    • Making a copy of only the object instance being cloned is called a shallow clone.
    • Making copies of all the objects referenced by the object being cloned is called a deep clone.
    • In general, the answer to whether you should make a shallow or deep clone of an object comes down to whether or not the object being cloned is mutable or not. In general, shallow clones are acceptable for immutable objects, or mutable objects that don’t refer to any other mutable objects, but not for mutable objects that refer to other mutable objects.
  • Cloning in Java
    • In Java, the Object class has a method called clone() which can make a shallow clone of the object.
    • It would seem, then, that every Java class supports shallow cloning automatically. But clone() is a protected method in Object. That means another object can’t call clone().
    • It is protected because Java insists that you grant explicit permission that it is safe to shallow clone your object by just copying its instance variables.
    • This permission is granted by having your objects implement the Cloneable interface.
      • Classes that implement Cloneable must implement a public method called clone.
      • This can either override the clone method in Object, or call it explicitly (which is allowed, because protected methods can be called by members of the same class or its descendants)
  • Deep Clones in Java
    • Deep clones are enabled in Java in much the same way as shallow clones.
    • Instead of calling the protected clone method in Object from our public clone method, we write our own custom code, appropriate to the data structure, to construct a deep clone.

7 — Abstract Data Types and ADT Specification

  • give a definition of a data structure
    • In a list, the data elements are usually all of the same kind, for example, integers, real numbers, character strings, or even a compound data type. In a list, the relationship between elements (the structure) is that each element has a rank in a linear ordering of elements.
    • In a tree, the elements are, again, usually all of the same kind (e.g. integers, character strings,
      etc.), and the relationship between elements is a hierarchical one: each element has a parent, and zero or more children.
  • give a definition of an abstract data type
    • An ADT is an abstraction that permits programmers to make use of a data structure without knowing its internal implementation.
    • A programmer knows what an ADT can do, but how it is done is hidden.
  • distinguish between the familiar term data type from the previous two terms
    • A data type is nothing more than the description of a kind of data (e.g. integer, floating point,
      character string), that is, the manner in which the bits and bytes of data in memory are interpreted.
    • A data type does not consist of a collection of elements, and therefore cannot have structure or relationships between elements. On the other hand, each of the elements of data that make up a data structure have a data type.
  • explain the advantages of using ADTs and encapsulation
    • We use ADTs because they specify the expected behaviour of a data type before it is implemented.
      • This facilitates the independent development and implementation of different ADTs by different programmers, and the development of reusable data types and objects by virtue of the public, and well-documented interface.
      • Changes and improvements to the implementation of an ADT can be made without affecting other parts of the program as long as the public interface and expected behaviour of the operations does not change.
    • Another advantage to using ADTs is that it postpones the development of details that are initially unnecessary.
      • For example, suppose a program requires a tree data structure. When designing the various components of the program, it probably isn’t that important to know whether the children of a node are stored in a linked list or an array. But the tree will have an agreed upon public interface which will allow the rest of the program to be designed, while the implementation details of the tree can be delayed until later.
    • Finally, ADTs allow complex data types to be designed independently from any particular programming language precisely because implementation is encapsulated.
      • If we specify the public interface in a programming-language-independent fashion, then we can delay the choice of programming language until much of the design process is complete, and we have a better idea of which programming language would be most suitable.
      • But we can still work with the ADT and even design algorithms using it because we can find out what it will be able to do when it is implemented by consulting the public interface.
    • Coupling is how much two pieces of code depend on each other. If one module directly uses a specific data structure (like a linked list), changes to that structure can force changes in the module too, which means high coupling. Using an ADT hides the implementation details, so modules only interact through a public interface, reducing coupling and preventing illegal changes to the data structure.
    • Cohesion is how closely related the parts of a module are. ADTs usually increase cohesion because all the code in the module focuses on one purpose—implementing that data structure.
    • Overall, ADTs improve software design by enforcing encapsulation, which leads to lower coupling and higher cohesion.
  • write programming-language-independent specifications of basic ADTs using the specification method discussed in Section 7.3
    • Our specifications are comprised of five things:
      • The name of the ADT
      • A definition of the sets used in the specification of the ADT
      • The signatures of the operations in the ADT, specified as functions defined on sets
      • The preconditions for each operation.
      • The semantics of each operation.
    • An ADT specification defines sets:
      • L = all instances of the ADT (all lists)
      • G = all possible items that can be stored in the ADT
      • B = Boolean values (true/false) for operations that return booleans
    • The ADT name often uses angle brackets ⟨G⟩ to show it stores elements from set G (this is just notation, not Java generics).
    • Operation signatures describe:
      • what set an operation acts on (e.g., L. means it operates on a list)
      • what inputs it takes and what it returns
      • if the output set matches the input set (L → L), the operation changes the state of the ADT
      • if the output set is different (like L → B), the operation returns a value
      • a crossed arrow means the operation is partial (only works when certain conditions are true)
    • Preconditions state when an operation is allowed (e.g., you can only get the first item if the list isn’t empty).
    • Semantics explain what the operation actually does to the ADT.

    • For Binary trees there are three specific traversals that have important significance. There are the pre-order, in-order, and post-order traversals. Only one valid one of these for every tree. All of these traversals involve three operations:
      • V: visit the node
      • L: traverse the left subtree of the node
      • R: traverse the right subtree of the node
    • Pre-order traversal
      • It’s a special case of the depth-first traversal. In the pre-order traversal, we start at the root, and then perform the above operations in the order: VLR. That is, every node is visited before both of its subtrees, and then we always traverse the left subtree before the right subtree.
      • The pre-order traversal of the tree in 9.2 is: R, A, B, C, D, E, J.
    • In-order traversal
      • Performs the traversal operations in the sequence: LVR, starting at the root.
      • That is the left subtree of a node is always traversed before the node is visited, and the right subtree of a node is always traversed after the node is visited.
      • The in-order traversal of the tree in 9.2 is: B, A, D, C, E, R, J
      • Note that the in-order traversal is not a breadth-first traversal: left child of a node t is always visited before t, and t is one level above its children. The in-order traversal is also not a depth-first traversal because in a depth-first traversal a node t is always visited before any of its children. In an in-order traversal, a node t is always visited after its left child.
    • Post-order traversal
      • The post-order traversal starts at the root and performs the traversal operations in the sequence: LRV.
      • That is, both the left and right subtrees of a node t are traversed before t is visited. Neither a breadth-first, nor depth-first traversal.
      • The post-order traversal of the tree in 9.2 is: B, D, E, C, A , J, R.

12 — Deletion from Ordered Binary Trees

  • list the three possible cases that can arise when deleting an element from an ordered binary tree
    • The node being deleted has zero children.
    • The node being deleted has one child.
    • The node being deleted has two children.
  • define the terms in-order successor and in-order predecessor
    • Given a node t, the in-order successor of t is the node containing the smallest element in the right subtree of t. It is named this because it is the node that would be visited immediately following the node t during an in-order traversal of the tree.
      • We will need to find the in-order successor of t in the deletion algorithm for a node with two children.
    • Similarly, the in-order predecessor of t is the node containing the largest element in t’s left subtree. This is because it is the node that would be visited immediately prior to t during an in-order traversal of the tree.
      • The in-order predecessor can be used in an alternate version of the deletion by copying algorithm.
  • explain the algorithms for deleting an element in each of the three cases
    • Deleting a node with zero children
      • Easiest case. If t has no children, then the requisite subtree of p can be replaced by an empty subtree without violating the ordering properties of any other nodes in the tree.
    • Deleting a node with one child
      • If t has only one child, r, then that child can become the replacement node for the subtree of p without violating the ordering properties.
    • Deleting a node with two children
      • If t has two children, then it would appear that we are in trouble. One of the children could be linked to t’s parent while preserving the ordering property, but then what should happen to the other child of t?
      • There are two common approaches for dealing with this problem. The one we will use is called deletion by copying. Deletion by copying works by converting the deletion problem from one of deletion a node with two children to one of a deleting a node with no more than one child.
      • Algorithm details
        • Suppose we are deleting node t and that its left and right children are r, and s, respectively.
        • Now, suppose we find the node that is the in-order successor of t; let’s call the element stored there e.
        • Further suppose that we copy e into node t, overwriting the element to be deleted, but not actually removing node t from the tree. Will this maintain the ordering properties?
        • By definition, everything in the subtree rooted at s is larger than anything in the subtree rooted at r. So copying e to t will not violate the property that everything in t’s left subtree have to be smaller than e.
        • Moreover, since e was the smallest element in t’s right subtree, then everything in t’s right subtree must be greater than or equal to e. So problem solved!
        • Well, except for the fact that we now have to delete the in-order successor of t because it contains the original (and now an extra) copy of e. How hard will it be to delete the in-order successor? Since the in-order successor contains the smallest element in the right subtree of t, the in-order successor cannot have a left child (otherwise there would have been a smaller element in the right subtree of t!). Therefore the in-order successor has at most one child, and is easy to delete.
      • Alternative algorithm
        • Note that we could alternatively use the in-order predecessor instead of the in-order successor as a replacement for the element in t. The effect on the collection of elements is the same, but the ordered binary search tree itself will have a different structure.
        • Some implementations make use of both options. For a given deletion, they choose the option which is most likely to maximize tree balance.

13 — Searchable Dispensers: AVL Trees

  • explain what the imbalance of a tree node is
    • A perfectly balanced binary tree is one in which there are h levels and every level is complete, that is there are as many nodes as possible on each level. h is thus the height of the tree.
    • In a perfectly balanced a tree of height h there are n = 2^h -1 nodes. Solving this for h, we get:
      • n = 2^h - 1
      • n + 1 = 2^h
      • log(n+1) = h
      • h = log(n+1)
    • This proves that in a perfectly balanced tree with n nodes, there are exactly log(n+1) levels, which means we can conclude that searching in a perfectly balanced tree is O(log n).
  • explain what the maximum imbalance of a tree is
    • It is important to be aware that imbalance is a property of a node in the tree, while maximum imbalance is a property of an entire binary tree.
    • It turns out that it is quite possible to modify the insertion and deletion algorithms of an ordered binary tree such that we can guarantee that the maximum imbalance of the tree is at most 1. It also turns out that a guaranteed maximum imbalance of 1 is enough to guarantee O(logn) searches. The AVL tree ADT does exactly this.
  • explain the AVL tree property
    • The AVL tree is a classic example of one of many so-called height-balanced or self-balancing search trees that have been devised over the years. It is named for its creators.
    • In other words, an AVL tree is an ordered binary tree where every node has an imbalance of at most 1. The trick is to figure out a way to make the insertion and deletion algorithms preserve this property. If we can do this, we will definitely succeed in guaranteeing an O(log n) search time because an AVL tree with n nodes has a height ≤2 log n.
    • Since AVL trees are ordered binary trees with a restriction on imbalance, we can immediately conclude that AVL trees are searchable dispensers (just like OBTs). The only different is the insertion and deletion algorithms are modified to guarantee a maximum tree imbalance of 1.
    • Suppose we have an AVL tree with a root node A, that has child nodes B and C, which are roots of subtrees of heights H1 and H2 respectively.
    • Now let’s supposed that we are inserting a new element e into this tree that happens to belong in the right subtree of node A. That is, the subtree rooted at C. Since this is an AVL tree, we know that H1 and H2 differ by at most 1. There are three cases to consider:
      • Case 1: h2 = h1-1 before insertion. In this case, the height of H2 is one less than that of h1, so if we insert into the subtree rooted at C, either its height doesn’t change, or is increased by 1. That means that the height of the subtree rooted at C after insertion becomes at most H2 = h1 - 1 + 1 = h1, so the AVL property is maintained without any extra work.
      • Case 2: H2 = h1 before insertion. In this case, the height of the subtree rooted at C again either doesn’t change or is increased by 1, which means that, after insertion, H2 = H! + 1 at most, and again, the AVL property is maintained without any extra work.
      • Case 3: h2 = h1 + 1 before insertion. In this case, still the height of the subtree rooted at C again either doesn’t change or is increased by 1. If it does increase by 1, then we have a problem because after insertion, we will have that H2 = h1 + 2, which means that A’s imbalance is 2 and that violates the AVL property. In this case, a modification must be made to the tree to restore the AVL property.
  • recognize the four situations of imbalance (which violate the AVL property) which can arise from insertion of an element into an AVL tree
    • The first two arise from case 3 in the previous section. When h2 = h1 + 1 and e gets inserted into the right subtree of A, there are two cases depending on which subtree of C the element ends up in. In Figure 13.3, we see that the new element e ended up in the right subtree of C, making C’s right subtree “heavier” than its left. Also, A’s right subtree is heavier than its left subtree. Since both A and C are right-heavy, we will call this an RR imbalance. As long as the only node in the entire tree with an imbalance greater than 1 is A, we can fix this easily. A is called a critical node because it is the root of an imbalanced tree in which all subtrees are sufficiently well-balanced. It is important to note that A is not necessarily the root of the entire tree. All of these situations also apply when A is the root of a subtree of some larger tree.
    • If instead, e ends up in the right subtree of A but the left subtree of C, then we have situation where A is right-heavy, but C is left-heavy, or an RL imbalance. Again A is a critical node — it has an imbalance of 2 and its descendants have an imbalance of no more than 1.
    • The other two situations that arise occur when the element e is smaller than the element stored in node A and the element ends up in subtree of B, and after insertion H1 = h2 + 2. This is an LL imbalance, and A is a critical node.
    • When e ends up in the left subtree of A and right subtree of B, this is an LR imbalance and A is once again a critical node.

  • describe the basic concept of a hash table
    • Hash tables store records that are keyed data items. Hash tables are implemented using arrays. The reserved location in the hash table array for an item is computed from the keyed data item’s key using a process called hashing. We say that we hash a value to an array index. This is done by a hash function applied to the item’s key.
    • Insertion of items into hash tables is achieved by obtaining an item’s key and hashing it to an array index. Then the item is put into the corresponding array location. Searching for an item with key k is also conceptually easy — hash k into an array index using the same hash function used by the insertion algorithm. If the item we’re looking for is in the hash table, it’ll be in that array index.

    • The load factor of a hash table is defined as:
      • LF = s/N
    • where s is the number of keyed items in the hash table and N is the size of the hash table array. In other words, it’s the ratio of the number of items in the hash table to the number of different indices.

    • When the load factor is small (let’s say, less than 1) then if our hash function is good, then we shouldn’t have more than 2 or 3 items hashing to any given index, and when we search for alternative indices using our collision resolution scheme, we will only have to look at a small, fixed number of indices, so searching is very close to O(1).
    • In general, assuming that our hash functions distribute items uniformly to indices, the average number of items hashing to the same index is equal to the load factor, and searching of alternate indices becomes O(LF).
    • Thus, in order to get close to constant-time performance for the search and insertion operations, we need to keep the load factor small. This can be achieved by increasing the size of the table array when the load factor gets too high. Typically, when the load factor exceeds 0.75, a new larger array is created, and all items already int he hash table are re-hashed to locations int he new array. While increasing the size of the array is expensive, it doesn’t have to be done that often, particularly if each time we increase the size of the array we double it. While this strategy maintains the efficiency of the operations, it does result in “wasted” memory, as there will always be hash table array entries which are not used.

  • explain the properties of a 2-3 tree
    • A 2-3 tree is another example of a height-balanced or self-balancing tree. We will see that a 2-3 tree is a keyed dictionary.
    • A 2-3 is an ordered tree in which every eternal node has exactly two or exactly three children, and all leaf nodes in a 2-3 are on the same level. Each leaf node stores a keyed data item. Internal nodes do not store data items.
    • Internal nodes store either one or two key values. If an internal node has two children (left and right), then it has only one key value k1. The items found in the leaves of the left subtree all have keys that are strictly smaller k1. Any items in the leaves of the right subtree must have keys greater or equal to k1. This kind of internal node is illustrated on the let side of Figure 16.1.
    • If, however, an internal node has three children (left, middle, and right) it has two keys, k1 and k2. The leaves of the left subtree contain items with keys strictly less than k1. The leaves of the right subtree contain items with keys greater than or equal to k2. This kind of internal node is illustrated on the right side of Figure 16.1.
    • In class, we will see how both types of node can be implemented using a single class/object which stores everything needed for a 3-node, but also keeps track of which keys and child references are actually used by the node, depending on whether it is representing a 2-node or a 3-node.
    • Recall that in order for a container to be a dictionary, it must support all of the operations of a linear iterator (i.e. a cursor that can be moved freely by the user). In a 2-3 tree, the properties mentioned above cause the items at the leaves of the tree (which, remember, are all at the same level) to be sorted in increasing order from left to right by their keys. This makes it easy to support the linear iterator operations necessary to make a 2-3 tree into a dictionary. We can add references to each leaf node that refer to the previous and next keyed data items in sorted order, and turn the bottom level of leaf nodes into a doubly linked list. Then it becomes easy to support a linear iterator. However, we have to add logic to the tree’s insertion and deletion operations to maintain those forward and backward references.
    • For the rest of this chapter and lectures, we will illustrate and discuss 2-3 trees assuming that the leaf nodes are not linked in this fashion so that it doesn’t clutter our understanding of the insertion and deletion operations. We may consider what happens when we add the extra leaf node references and linear iterator operations in a programming assignment.

17 — Dictionaries: B+ Trees and B Trees

  • define the properties of B+ trees and B trees
    • B+ trees are a generalization of the 2-3 trees. In a B+ tree of order b, each internal node has between [b/2] and b children (except the root which may have between 2 and b children).
    • Similar to 2-3 trees, leaves in a B+ tree store keyed data items and internal nodes contain up to b-1 keys that partition the ranges of keys that can be found in the subtrees rooted at each child.
    • Internal nodes contain between [b/2] - 1 and b - 1 keys, always one less than their number of children (with the exception of the root which can have between 1 and b - 1 keys because it can have as few as two children).
    • Again, like 2-3 trees, B+ trees also link the leaf nodes into a singly or doubly-linked list to facilitate accessing the elements in the tree sequentially in order of their keys. The 2-3 trees that we previously studied (with the leaf nodes linked into a list) are exactly B+ trees of order 3.
    • The insertion and deletion from B+ trees are generalizations of the same operations for 2-3 trees. Upon insertion, if a node needs to have more than b children, then it is split, and the new node must be accommodated by the split node’s parent, which may, in turn, cause other splits. If deletion results in a key have fewer than [b/2] children, then stealing or giving will occur similar to the way it occurs when deleting from a 2-3 tree.
  • relate B+ trees to 2-3 trees in terms of their similarities and differences
    • A 2–3 tree is conceptually similar to a B+ tree of order 3, but they are not exactly the same in implementation.
    • In a 2–3 tree (as defined here), each data item has its own leaf node, and internal nodes can have up to 3 children.
    • In a B+ tree, leaf nodes are combined (collapsed) so that each leaf stores multiple data items instead of one per node.
    • Because of standard B+ tree rules, a leaf node in a B+ tree of order 3 can store at most 2 keys, not 3.
    • This creates a key difference: in the 2–3 tree definition, nodes above the leaves can effectively correspond to up to 3 leaf children, whereas in a B+ tree of order 3, this structure is more constrained.
  • relate B trees to OBTs in terms of their similarities and differences
    • B trees are generalizations of OBTs. They are very similar to B+ trees, except that in B trees, not all keyed data items are stored at the leaves. Instead of storing just keys, internal nodes store keyed data items (often more than one), but the keys of those elements also serve as partitioning keys for the ranges of keys in the subtrees of the node’s children, just as the keys in the internal nodes of a 2-3 tree do.
    • Nodes in a B tree of order b have between [b/2] and b children (Except the root which may have as few as two children).
    • Insertions use a form of splitting similar to B+ trees, deletions use stealing and giving similar to B+ trees. This ensures that the tree is balanced; all leaf nodes in a B tree are at the same level (even though not all elements are stored in leaves).
    • The leaves are not linked in a list because the leaves do not contain all of the keyed data items in the tree and therefore linking the leaves cannot facilitate sequential access to all items in key-order.
  • compare the advantages and disadvantages of B+ trees and B tree relative to each other
    • The main advantage of the B+ tree over a B tree is that, since all of the elements are at the leaves in a B+ tree, it facilitates much better sequential access to the elements (b/c they can just be read from left-to-right along the leaf level.
    • On the other hand, B tree would be preferred for random accesses since, on average, random searches would be slightly faster (by a constant factor) in a B tree because of the possibility of finding a desired element before reaching the bottom level of the tree.
    • Both B trees and B+ trees have an O (log n) worst-case time complexity for searching, insertion, deletion where n is the number of keyed data items in the tree. The best case time complexities, however, differ, with the B tree being more efficient in certain circumstances for the price of giving up efficient key-order iteration.
  • describe why B+ trees and B trees are advantageous for disk-based data structures
    • B+ trees are used a lot in the implementation of filesystems and databases. This is because in these applications the data elements (and the tree itself) may be stored in data blocks on a disk rather than in RAM. Because high-order B+ trees have a very high fanout, fewer I/O operations (which are relatively very expensive) are needed versus an implementation that uses a binary tree structure. This is because the B+ trees have fewer levels when storing the same number of items compared with a binary tree. Since searching the tree would require accessing a different disk block at each level, the B+ tree would require much fewer disk block accesses, and thus fewer disk I/O operations (which are spectacularly expensive compared to accessing data from main memory).
    • Several filesystems use B+ trees for metadata indexing include NTFS, ReiserFS, NSS, XFS, JFS, and ReFS. B+ trees are also used in many relational databases (where again, data is stored on disk) such as IBM DB2, Informix, Microsoft SQL Server, Oracle 8, Sybase ASE, and SQLite to record table indices.
    • Like B+ trees, B trees are useful for disk-based data structures because the high branching factor minimizes disk accesses. The max number of children is usually governed by the disk block size, which, in turn, governs how many keyed data items pairs can fit in a disk block. Thus, each node is associated with a disk block, and each node visited in a search operation causes one disk access. The high branching factor reduces the height of the tree, which keeps the number of disk accesses needed to search for an element very small.

    • A trail that begins and ends on the same vertex is called a circuit.
    • A path is a walk that does not visit any vertex more than once except the first and last vertex on the path may be the same.
    • A path that starts and ends on the same vertex is called a cycle.
    • The length of a walk/trail/path/circuit/cycle is the number of edges in the thing.

  • Data Structures for graphs
    • Suppose we have a graph G = (V, E) with |V| = n (i.e. there are n nodes in the graph). Further suppose that we assign to each node in V a unique integer index b/t 0 and n-1. We can do this renaming w/o loss of generality as long as the new node names are unique. Thus, in the rest of this chapter we will assume that V = {0, 1, 2, …., n-1} for all graphs.
  • Storing nodes
    • Most graph algos tend to require access to nodes in a graph in a more or less random order rather than sequentially. Therefore, we must have the ability to access a specific node quickly. Usually the # of nodes in a graph either doesn’t change, or an upper bound is available. Therefore, it is not unreasonable to store the nodes of a graph in an array. In Java, we might create a node object, and then store the nodes in the graph in an array of that object’s type.
    • Storing graph nodes in an array allows us to access a specific node i in the graph in constant time, which is perfect for the random access patterns to nodes that we anticipate. We can find a desired node by indexing into that array that stores the nodes using the index of the desired node.
  • Storing edges
    • A desired edge is usually accessed by specifying its source and destination nodes. There are 2 common types of access patterns that one finds in algos that operate on graphs.
    • The 1st typical edge access pattern is: given 2 vertices, access the edge b/t them (if it exists) that is, a request to access a specific edge.
      • Random access pattern similar to the access pattern we anticipate for nodes. Thus, it would be wise to adopt a mechanism for storing edges in which a specific edge can be accessed quickly.
    • 2nd: given a vertex, access its outgoing edges one-by-one.
      • Sequential access pattern.
      • Might occur in a traversal of the graph, in which having visited a vertex, the algo must then visit all of that vertex’s immediate neighbours.
      • Thus, it would be wise to adopt a mechanism for storing edges that facilitates efficient sequential access to all outgoing edges from a given vertex.

21 — Graph Traversals

  • explain and distinguish b/t strategies of breadth-first vs depth-first traversal
    • Graph traversals are algorithms for visiting the nodes of a graph in systematic order. Similar to list or tree traversal algos for this reason, b/c they also visit every node or element. For graphs, there are two basic strategies for making traversals:
      • if the current node is v, visit each node directly adjacent to v before considering nodes that are further away. (Breadth first)
      • if the current node is v, recursively visit an adjacent node and all nodes further away before considering the next node adjacent to v. (Depth first)
    • The algos will somewhat resemble the breadth- and depth-first traversal algos for trees b/c trees are special cases of graphs.
    • Main differences are caused by the need to deal with the fact that, unlike trees, graphs may contain cycles which could cause a traversal to arrive back at an already-visited node.
  • find a valid breadth-first traversal of a given graph
    • To start a breadth-first traversal, a starting node is selected, and is visited.
      • Recall that “visiting” a node means to perform some relevant operation with or on any data associated with the node.
    • Then, the breadth-first traversal then visits all nodes that are reachable by a path of length 1 from the start node.
    • Once these are exhausted, nodes that are reachable via a path of length 2 from the start node are visited, and so on.
    • It is important to note that for most graphs, the order in which nodes are visited in a breadth-first traversal is not unique.
    • Another way to look at the breadth-first traversal is to find the shortest paths from the start node to each other node, and then remove any edges that do not appear on any such shortest path. The result will be a subgraph which is a tree. The tree is called the shortest path tree. A breadth-first traversal traverses only the subgraph corresponding to the shortest path tree, which is always traversed in level-order.
    • find a valid depth-first traversal of a given graph
      • The depth-first approach is similar to finding one’s way out of a maze. Once the traversal starts down a path, it continues along the path visiting new nodes as long as possible. When a previous vertex (”dead end”) is reached, we back up and take the first available alternate path. In this way, the depth-first traversal continues to try different paths until all possible paths that don’t lead to already visited vertices have been tried.
      • The right side of Figure 21.3 shows the subgraph of the left side of said figure that consists of only the red edges and drawn as a depth-first tree. So again, we see that, like breadth-first traversal, depth-first traversal follows the edges of a subgraph of the graph that is a tree. But note that the tree followed by a depth-first traversal it isn’t a shortest-path tree as in the case of breadth-first traversal! The path in the depth-first tree from node 1 to node 4 is of length 2, but the shortest path from node 1 to node 4 is of length 1.
      • The algorithm for depth-first traversal of graphs, given below, is nearly identical to the algorithm for depth-first traversal of trees. We needed to add a test for whether the node we are about to visit has already been visited via another path. We also needed an initial method to set each vertex’s “reached” property to false, then the familiar depth-first algorithm appears in a recursive helper method.
    • Like breadth-first traversals of graphs, depth-first traversals of graphs are not unique. We make no promises about the order in which the loop for each node u adjacent to v processes adjacent nodes. As long as the current path from the start node is always made longer, if possible, the next node to be visited can be chosen from among the non-visited adjacent nodes in any order, and the result is still a depth-first traversal. In practice, the data structure used to store edges (adjacency list or adjacent matrix) usually imposes a convenient order.

  • explain Warshall’s algorithm
    • The algo for path existence computes the answer to the question: “Is there a path from node i to node j (of any length)?” for two given nodes i and j. We can use the powers of the adj matrix from the previous section to answer this question. To see how, we must first establish the following claim:
      • If there a walk from i to j of length r, then there must be a path from i to j of length n-1 or less (n=number of nodes in the graph)
        • A graph has n nodes
        • If you walk longer than n-1 steps:
          • you must repeat a node → there is a cycle, and cycles can be removed
          • So any long messy walk can be shortened into a simple path
        • If you visit a node twice → you looped, so that loop is useless, cut it out and you get a shorter path
      • How matrices help:
        • A^1 → paths of length 1, etc. So if we check all powers up to n-1:
          • B = A + A^2 + A^3 + … + A^n-1
          • B(i, j) means if any of those matrices had a path, it adds up.
        • But computing one matrix multiply = O(n^3), and you do it n times, for a total of O(n^4). Warshall’s algo is faster.
        • Modify the algorithm to return path existence for all pairs of nodes → change last line to return B, time complexity is the same
    • Warshall’s algo: we need to define a new kind of matrix. Let P^(k) be a binary matrix (entries are 0 or 1) where P(k)(i, j) = 1 if and only if there is a path from i to j that passes through intermediate vertices {1, 2, …, k} only. That is, P(k)(i, j) =true only if there is a path that starts with i, ends with j, and contains no other vertex numbered higher than k.
      • Note that if we can compute P(n) then we have solved the problem because there are no nodes in the graph numbered higher than n; P(n)(i, j) would be true only if there was a path in the graph from i to j.
    • Time complexity: Warshall’s algorithm has three nested loops. In the worst case, the body of the innermost loop is O(1). The inner loop body runs n times and therefore the entire inner loop costs O(n). The middle loop runs the inner loop n times, each run costs O(n) so the total cost of the middle loop is O(n2). The outer loop runs the middle loop n times, and each such run of the middle loop costs O(n2) time so the outer loop costs O(n3). Beyond the outer loop there are just two additional statements, so the total time is O(n3) + 2 or just O(n3). The best case is the same as the worst case, so Warshall’s algorithm is Θ(n3).
