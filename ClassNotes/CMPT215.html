Performance - Jan 9, 12

Reference: Sections 1.6, 1.9, 1.11

  • “How fast does my code run?” but not quite as simple as that owing to parallelism (might get speedup by doing more things simultaneously rather than any one thing quicker, e.g. massive parallelism in Google’s implementation of search …)
  • Two system-level metrics are response time and throughput (e.g. for Google search, how long does it take to get a response to a search request? At what rate can the system process requests?)
  • Overall system performance can depend on more than just the processor (e.g., secondary storage devices, network links, …)
  • However, we will focus for now just on the metric of CPU execution time … i.e., how long it takes a single “CPU” (processor core) to execute some sequence of instructions
  • CPU execution time as the product of 3 factors
  • CPU execution time = (instruction count) x (clock cycle time) x CPI
    • Instruction count: The number of machine language instructions executed
      • Depends on:
        • high-level language program
        • compiler
        • “instruction set architecture” (ISA) (how rich is the instruction set? One system might have a powerful machine language instruction that can do a complex operation (e.g., a vector operation that takes a sequence of instructions on another system … historically important distinction between RISC — “reduced instruction set compiler” and CISC — “complex instruction set computer”)
    • Clock cycle time: processors rely on a clocking signal to time their operations, the “clock cycle time” is the time between clock “ticks”
      • Each step of instruction execution requires one clock cycle to complete
      • Very short … commonly measured in nanoseconds (one nanosecond is one billionth of a second, i.e. 10^-9 seconds), or in picoseconds
      • Depends on:
        • Architecture implementation
      • Clock cycle time = 1 / clock rate (be careful regarding units)
        • Clock rate commonly measured in GHz (billions of cycles per second)
        • e.g., if clock rate is 2 GHz, clock cycle time is 0.5 nanoseconds (=500 picoseconds)
      • In the past, clock cycle time of a processor was fixed, but now often can be dynamically varied (and so it’s actually the average clock cycle time that is a factor in the CPU execution time)
    • CPI (”cycles per instruction”): to simplify things, we will assume for now that instructions are executed one-by-one, without pipelining (later in the course we’ll see how idea can be generalized)
      • CPI without any subscript is used
    • Example: suppose 4 GHz clock rate,
      800 million instructions
      CPI = 1.5
      CPU execution time = 800 x 10^(9) x 1.5 x (1/4 x 10^-9) = seconds

CPI (“cycles per instruction”): to simplify things, we will assume for now that instructions are executed one-by-one, without pipelining (later in the course we’ll see how idea can be generalized)

  • CPI without any subscript is used for the average number of clock cycles required per instruction executed
  • different types (classes) of instructions can have different average execution times, use CPIc for the average number of clock cycles required for an instruction of class c
    • Example: suppose we have two types of instructions A and B; CPIA= 5, CPIB=1; what is the CPI?
    • CPI can be expressed as a weighted average, where the weight for an instruction class c is the fraction of the executed instructions that are class c instructions (note that program dependent !!)
  • CPI = ∑fc x CPIc, where fc is the fraction of instruction type, and CPIc is the cycles for that instruction.
    • In previous example, suppose 200 million type A instructions were executed, 300 million type B … now we know enough to calculate the CPI (what is it?)
  • Another formula for CPI: total # clock cycles required for program execution / total # machine language instructions executed
  • CPI depends on:
    • ISA
    • architecture implementation
    • high-level language program
    • compiler
  • Example: if new compiler reduced # class B instructions executed by 50%, by what factor would CPU execution time decrease?
    • two types of instructions A and B;
      CPIA= 5,
      CPIB=1;
      40% of executed instructions are of type A, 60% are of type B
    • let C denote original instruction count
      original # class A instructions executed = 0.4C
      original # class B instructions executed = 0.6C
      original CPI = 2.6
      new # class B instructions executed = 0.3C
      class A instructions executed is unchanged (= 0.4C)
      new instruction count = 0.4C + 0.3C = 0.7C
    • new CPI = (new fraction of instructions executed that are of type A)xCPIA + (new fraction of instructions executed that are of type B)xCPIB
      • new fraction of instructions executed that are of type X = (old class X instructions executed) / (new total instruction count)
      • new CPI = ((0.4C/0.7C) x 5)+((0.3C/0.7C) x 1) = 23/7
    • and so ratio of new execution time to old execution time is given by: (0.7C x new CPI x clock cycle time / (C x original CPI x clock cycle time)
      = (0.7 x new CPI)/original CPI
      = 0.885

Amdahl’s law: the performance improvement possible with a given system improvement is limited by the amount that the improved feature is used

  • new execution time = (portion of execution time affected by improvement) /(improvement factor) + portion of executiontime unaffected
  • or alternatively, ratio of new to old execution time = (fraction affected) /(improvement factor) + fraction unaffected

  • in previous example problem:
  • fraction affected = (time spent executing type B instructions)/(total execution time) = (0.6 x original instruction count x 1 x clock cycletime)/(original instruction count x original CPI x clock cycle time) = ??
  • fraction unaffected = 1 – fraction affected
  • improvement factor is 2
  • so, new/old = (fraction affected) / 2 + fraction unaffected = ??

How should the performance of different computer systems be compared?

  • Clock rate?
    • But this is just one of the three factors in our formula for CPU execution time
  • MIPS? (”millions of instructions per second”)
    • MIPS = (clock rate in GHz) x 1000 / CPI
    • but this reflects just two of the 3 factors
    • Program dependent
  • MFlops? (”millions of floating point operators per second”), or more appropriately, given increases in performance that have occurred, GFlops, TFlops, PFlops, or Eflops
    • Notion of an “operation” more architecture dependent than that of a machine language instruction
    • Like MIPS, program dependent

El Capitan, a supercomputer installed at the Lawrence Livermore National Laboratory in the US, is currently #1 on the “top 500” list of the fastest publicly-announced computers, and has achieved a processing rate of over 1.8 EFlops (1.8 quintillion floating point operations per second) on the “High Performance Linpack” benchmark

  • Configuration includes 11,340,000 processing cores in total
  • Power consumption of about 30 megawatts

Benchmarks: Programs written in a high-level language chosen to serve as the basis of performance comparison between systems.

  • Synthetic
  • Kernels / simple routines (e.g. Linpack)
  • Real applications (e.g. as standardized by SPEC — “Standard Performance Evaluation Corporation”)

How to summarize results from running a suite of benchmarks?

SPEC uses the geometric mean, with each execution time measured relative to that on a (standardized) reference machine

  • e.g. suppose have 3 benchmarks, with execution times on system A of 3, 2, and 9, respectively
  • Suppose further that on the standard reference machine, these execution times were 10, 8, and 20, respectively
  • Then the SPEC rating for A would be the cube root of (10/3) x (8/2) x (20/9)
  • In general, with N benchmarks, would take the Nth root of the product of the N relative execution time factors.

Power - Jan 12

  • Clock rates no longer increasing, owing to power consumption considerations
  • With current technology, “dynamic” power consumption is proportional to V^2 x f, where V is the voltage and f is the transistor switching frequency
    • f is proportional to clock rate; also often lower V can be used when clock rate is lower
  • Power wall … can’t keep increasing clock rate owing to problem of cooling the processor chip!
  • Also have “static” power consumption resulting from “leakage current” that flows even when transistors are not being switched.
  • How to power consumption?
    • Use simpler processor designs with fewer transistors
    • Cut off clocking signal to components that aren’t currently in use, eliminating dynamic power consumption by those components
    • Cut off power to components that aren’t currently in use, eliminating both dynamic and static power consumption by those components.
    • System sleep states
  • In light of the “power wall”, how have we continued to make dramatic improvements in performance?
    • Most prominently, specialization of processing components for specific computations or types of computations (e.g., specialized cores & accelerators in smartphones, GPUs, Google’s Tensor Processing Unit (TPU), … )

Introduction to RISC-V Assembly Language - Jan 12, 14

Reference: Text sections 2.1-2.3

  • RISC-V has a modular design, with a number of alternative “base” parts and optional “extensions” for the base, we will be using RV32I .
  • Example extensions are the F and D extensions for floating point, but there are many others
  • See here for RISC-V instruction set manual
  • Registers and memory
    • In assembly language, programmer works directly with hardware storage elements called registers
      • High-speed storage locations on the processor chip … only have a small number of these
    • Registers used to store data that the program is currently operating on (also some special purpose uses)
    • Assembly language programmer also uses a memory space
      • Implemented using the computer system’s “main memory” (typically implemented on separate chips than the processor and much, much slower to access than the registers … but have a lot of it! e.g. 8-32 GB on a typical laptop), plus (as we’ll see later in course) processor cache memory
  • In the RISC-V base we will be using (RV32I), have 32 registers, each 32 bits (inside back cover of text has listing)
  • The memory space (in RV32I) can be viewed as an array of 8-bit bytes
    • The index of a byte in this array is its memory address
    • The first byte in memory has memory address 0, the second byte has memory address 1, the third byte has address 2, and so on
    • Memory addresses are 32-bits, the same as the register size (→ largest possible address is 2^(32)-1)
  • Can also view memory as consisting of 32-bit (i.e. 4 byte) words
    • The memory address of a word is the address of its first byte; e.g. the word with memory address 20 contains the bytes with addresses 20, 21, 22, and 23
    • Many architectures have an alignment restriction, requiring words to start at an address that is a multiple of the word size (in this case, a multiple of 4)
    • RISC-V does not have such a restriction in general (although, in RV32I, machine language instructions must be aligned on a four-byte boundary)
  • Little-endian versus big-endian
    • When storing a 32-bit binary integer value in a memory word, do the bytes within the word with higher addresses store the leftmost (”higher-order”) bits of the integer (this is the little-endian convention, and is used in our environment) or is it the other way around?
      • e.g. 97 as a 32-bit binary number is: 00000000000000000000000001100001
        if store this in the memory word with address 20 (which consists of the bytes with addresses 20, 21, 22, and 23), which bits does the byte with address 23
        get?
    • Becomes an issue when transmitting integers and other multi-byte items between systems that may use different conventions

Branch Instructions - Jan 19

  • In addition to “beq” and “bne”, we have some other branch instructions: “blt”, “bltu”, “bge”, and “bgeu”.
    • The “u” suffix indicates that register contents should be interpreted as unsigned integers when doing comparison.
    • Registers are just bits. The CPU decides whether those bits represent:
      • signed two’s complement (… −2, −1, 0, 1, 2 …)
      • unsigned (… 0, 1, 2 … 2³²−1)
    • Example: 0xFFFFFFFF
      • signed = −1
      • unsigned = 4294967295
  • There are also branch pseudoinstructions.
    • “bgt”, “bgtu”, “ble”, “bleu”
    • “beqz”, “bnez”, “bgtz”, “bgez”, “bltz”, “blez” for comparisons against zero, e.g. “blez s1, loop”
  • A pseudoinstruction does not have a directly corresponding machine language instruction; instead, assembler must implement using one or two real instructions that achieve the desired result.
    • for “bgt”, “bgtu”, “ble”, “bleu”, just need to reverse operands and use “blt”, “bltu”, “bge”, “bgeu”, respectively
    • How about for “beqz”, “bnez”…?
      • These are comparisons against zero.
        • beqz rs, L → beq rs, x0, L
        • bnez rs, L → bne rs, x0, L
      • The others are similarly “compare vs x0”:
        • bgtz rs, L → blt x0, rs, L (0 < rs)
        • bgez rs, L → bge rs, x0, L (rs ≥ 0)
        • bltz rs, L → blt rs, x0, L (rs < 0)
        • blez rs, L → bge x0, rs, L (0 ≥ rs)

        So: they’re just real branch instructions using x0 as the other operand.

    • Other pseudoinstructions include “mv” (how could this one be implemented?), “li”, “j”, “jr” (address to go to is in a register rather than given as a label), and “la”! (we’ll see later how these last four can be implemented …)
      • mv rd, rs is a pseudo for:
        • addi rd, rs, 0
        • Because adding 0 copies the register.
    • also a convenient pseudoinstruction form of “lw/lb” (e.g. “lw s0, A”) … but “sw/sb” not so simple … why?
      • You can write lw s0, A as pseudo because it means:
        load from memory at address A (a label)
    • Assembler can expand it into:
      • load address of A into a temp register
      • then lw s0, 0(temp)

      Example expansion conceptually:

      la t6, A
lw s0, 0(t6)
      • So why is sw s0, A “not so simple”?
        • Because sw needs two pieces of information:
          • the data register to store
          • the address to store to

      To emulate sw s0, A, assembler would still need a temp register for the address:

      la t6, A
sw s0, 0(t6)
      • It consumes a temporary register.

        For loads, assemblers can often hide this more safely because the destination is being overwritten anyway, and some assemblers have conventions for temp usage.

        For stores, the source register holds important data, and using temps can clash with programmer expectations / register allocation / macro expansion rules.

        In other words: implementing sw reg, label as a pseudo is doable, but it’s less “safe”/predictable because it requires an extra register that the assembler must “steal.”

        (Some assemblers still provide store pseudos in certain modes, but many courses avoid it for exactly this reason.)

Representations of signed integers - Jan 23

  • Sign-magnitude
    • One bit used for sign (0-positive, 1-negative)
    • Remaining bits give absolute value of number in binary
    • e.g. -3 would be represented as 10 … 011
    • With n bits, range is −(2n−1−1) to 2n−1−1
    • Disadvantages: two representations of zero; hardware circuits implementing arithmetic operations are relatively inefficient
  • One’s complement
    • Representation of non-negative integers same as with unsigned
    • Get representation of -x from that of x by changing all 1s to 0s and 0s to 1s
    • e.g. -3 would be represented as 11 … 100
    • Still two representations of zero, but more efficient arithmetic implementations!
    • (to add two one’s complement numbers, add them using ordinary binary addition, and then if there is a carry out from the leftmost bit position, add 1 … try it!)
    • Not used currently for computer system representation of signed integers, but does have an application in Internet communication, for “packet checksums” …
  • Two’s complement: representation of signed integers that is currently used in computer systems
    • Representation of non-negative integers same as with unsigned
    • Get representation of -x from that of x by changing all 1s to 0s and 0s to 1s, and then adding 1
    • e.g. -6 would be represented as
      • 00 … 0110 → 11 … 1001 + 1 = 11 … 1010
      • Above method for finding -x also works for negative x!
      • 11 … 1010 → 00 … 0101 + 1 = 00 … 0110
    • Negative numbers all have 1 as left-most bit (same as with sign-magnitude and one’s complement)
    • With n bits, range is −2n−1 to 2n−1−1
    • Now only one representation of zero, and efficient arithmetic implementations
    • Example of two’s complement representation when n=4 (when have just 4 bits to represent a number)
  • Addition with two’s complement numbers: can just use ordinary binary addition
    • Note that any carry out of the left-most bit position gets discarded
  • Subtraction of two’s complement numbers: find the negative of the number you’re subtracting, and add
    • x-y → x + (-y)
    • (remember how to find negative — flip all bits, add one … )
  • … but need to be aware of possibility of overflow
    • Overflow is when correct result is not representable in the available number of bits
    • Two kinds of overflow: unsigned overflow, and signed overflow
    • e.g. suppose we have just 4 bits to represent a number
  • What is done when overflow occurs?
    • In RISC-V, nothing automatically … up to program to check for overflow if want such a check
    • Example: checking for unsigned overflow of addition operation

      add s0, s1, s2 # want to check this for unsigned overflow

      bltu s0, s1, overflow # why does this work?

      Reason: with unsigned addition, if there’s no overflow, then:

      • s0=s1+s2≥s1 (because s2≥0 in unsigned world)

      If there is overflow, the sum “wraps” back around near 0, so the result becomes smaller than one of the addends (commonly checked against s1 or s2):

      • overflow ⇒ s0<s1 (or s0<s2)

      That’s why the branch catches it.

    • Example: checking for signed overflow of addition operation:

      add s0, s1, s2 #want to check this for signed overflow

      slti t0, s2, 0 # t0 ← 1 if s2 < 0, otherwise t0←0

      slt t1, s0, s1 # t1←1 if s0 < s1, otherwise t1 ← 0

      bne t0, t1, overflow # why does this work?

      Interpret what should happen:

      Case A: s2 >= 0 (t0 = 0)

      Normally adding a nonnegative number should not make the result smaller:

      • expect s0≥s1⇒ s0<s1 is false ⇒ t1 = 0

        So t0 and t1 match (0 == 0) → no overflow.

      If overflow happens in this case, it’s positive overflow:

      • adding a positive pushes past max int → wraps to negative
      • result becomes smaller than s1 ⇒ t1 becomes 1

        Now t0=0, t1=1 → mismatch → overflow.

      Case B: s2 < 0 (t0 = 1)

      Normally adding a negative should not make the result bigger:

      • expect s0<s1 ⇒ t1 = 1

        So t0 and t1 match (1 == 1) → no overflow.

      If overflow happens here, it’s negative overflow:

      • adding a negative pushes past min int → wraps positive
      • result becomes not less than s1 ⇒ t1 = 0

        Now t0=1, t1=0 → mismatch → overflow.

      So bne t0, t1 works because overflow is exactly when the expected direction of change fails.

    • How could you check for (signed, unsigned) overflow on subtractions?
      • A) Unsigned subtraction overflow (borrow)

      Unsigned underflow occurs when you subtract a larger number from a smaller one:

      • underflow/borrow ⇔ s1<s2
      sub  s0, s1, s2            # s0 = s1 - s2 (unsigned)
bltu s1, s2, overflow      # if s1 < s2, borrow happened

      (Alternative check: after subtract, if s0 > s1 unsigned, also indicates borrow, because wrap makes it large.)

      B) Signed subtraction overflow

      Signed subtraction overflow happens when:

      • s1 and s2 have opposite signs, and
      • the result’s sign is different from s1

      Rule summary:

      • s1−s2 overflows if
        • s1≥0 and s2<0 and result < 0 (positive overflow)
        • s1<0 and s2≥0 and result ≥ 0 (negative overflow)

      One clean way (mirrors your add trick) is to check signs:

      sub  s0, s1, s2

slti t0, s2, 0        # t0 = (s2 < 0)
slti t1, s1, 0        # t1 = (s1 < 0)

RISC-V Machine Language - Jan 23, 26

  • Simplified model of instruction execution
    • Repeat forever:
      • Load instruction whose address is in PC into IR
      • Decode
      • Execute instruction
      • Increment PC by instruction length
    • The PC (”program counter”) holds memory address of instruction to be executed.
    • The IR (”instruction register”) holds the instruction being executed
  • Above simple model suggests that implementing a fast processor will be easier if we have:
    • fixed length instructions
    • compact instructions
    • only a few instruction formats with consistent field locations
  • In RISC-V RV32I, fixed length (32 bits — one word) instructions, with four core formats
    • R-type – register-to-register operations (e.g., add, sub)
    • I-type – register + immediate, loads, system calls
    • S-type – stores
    • B-type – conditional branches

      (Plus U-type and J-type for large immediates and jumps)

  • Some significant design features
    • rd: destination register, rs1: source register 1, rs2: source register 2 (used only in instructions needing 2 inputs, like add/sub).
    • immediate (imm): A constant number stored directly in the instruction.
      • Used for: addi, loads/stores, branches
      • Important: immediates are often sign-extended and size depends on format
    • The opcode field uniquely identifies the operation only for U,J-type instructions; for the other instruction types, determines the instruction format, but also need the funct field(s) to identify the particular operation (why not just have a longer opcode field?)
      • The opcode is the main field that says “what kind of instruction is this?”
      • Why funct3 and funct7 exist
      • For R-type, I-type, S-type, B-type:
      • The opcode mainly says: “This is an R-type ALU instruction”
      • But which ALU operation? That’s where: funct3 (3 bits) funct7 (7 bits) come in.
      • opcode → instruction class
        funct fields → specific operation
    • 5 bits for each register number (why do you think RISC-V has 32 registers rather than, say, 128?)
      • If RISC-V had 128 registers:
        • Need 7 bits per register
        • R-type instruction would need 21 bits just for registers
        • Almost no room left for opcode/immediates
      • 32 registers is the sweet spot
        • Enough for compilers
        • Fits cleanly in 32-bit instruction format
        • Classic RISC choice (MIPS, ARM followed same idea)
    • The numbers of the register operands always occur in the same places (can read in parallel with decoding!)
    • no space for full-sized (32-bit) immediate operands (obviously since an entire instruction is just 32 bits!), so dealing with immediates can get a bit messy…

Examples of RISC-V Machine Language Instructions - Jan 26

  • How about “addi s0, s1, 5000?” … Illegal since constant is too big to fit in 12 bit field. Instead, you can use a sequence of three instructions, starting with lui to fill in the top 20 bits of s0.
  • First, the instruction lui is used. LUI stands for “load upper immediate.” It puts a value into the upper 20 bits of a register and fills the lower 12 bits with zeros. When you load the value 1 into the upper bits of register s0, the register ends up holding 4096. That gets you most of the way to 5000.
  • Next, you add the remaining amount using addi. The difference between 5000 and 4096 is 904. That smaller number does fit in the 12-bit immediate field, so you add it to the register. Now the register holds 5000.
  • Finally, if the original goal was to add 5000 to another register (s1), you then add that register’s value to the result.
  • lui
    addi
    add
  • What la s0, A actually does
    • When you write something like load the address of A into s0, the assembly usually does not know the exact memory address ahead of time. Instead of hard-coding an absolute address, it builds the address relative to the program counter (PC).
    • To do this, it uses the instruction auipc (Add Upper Immediate to PC)
  • What auipc does
    • auipc uses the U-type format, just like lui.
    • It takes a 20-bit immediate value, shifts it left by 12 bits (adding 12 zeros at the end), and then adds that value to the current PC.
    • So after auipc runs, the register contains: PC + (upper immediate << 12)
    • Then an addi instruction usually follows to add the lower bits of the address. Together, auipc + addi build a full 32-bit address.
    • This is called position-independent code. It means the program can run anywhere in memory because addresses are built relative to the current location instead of being fixed.
    • Why it’s important: If programs had fixed memory addresses, they would break if loaded somewhere else. By using PC-relative addressing, the program works no matter where it’s placed in memory.
  • How branches work
    • Branch instructions like beq also use PC-relative addressing.
    • Instead of storing a full address, they store a small offset from the current PC.
    • Important facts:
      • Branch offset is 13 bits total (after sign extension)
      • Only 12 bits are stored in the instruction
      • One extra zero bit is added on the right
      • Because of that zero bit, the offset must be a multiple of 2.
      • Why is that reasonable?
        • Because RISC-V instructions are aligned in memory, so jumps always land on valid instruction boundaries.
  • Examples of a branch:
    • If a branch skips one instruction and lands two instructions later, the offset is calculated relative to the PC.
    • The encoded immediate bits are split across the instruction in a special format (B-type)
  • Key ideas
    • auipc builds addresses relative to the PC
    • It loads upper bits, then addi finishes the address
    • Used for position-independent code
    • Branches also use PC-relative offsets
    • Branch offsets must be multiples of 2
    • Offsets are sign-extended to 32 bits

How do other machine/assembly languages compare to RISC-V? - Jan 30, Feb 2

Reference: text page 125, Section 2.24

  • Basic styles of machine language
    • “load-store” (or “register-register”) style
      • This is what RISC-V
      • Arithmetic/logical instructions have 3 operands, all of which must be registers except possibly for the last which can be a constant
    • “accumulator” style
      • Only a single register (”accumulator”)
      • Accumulator is an implicit operand
      • e.g. to implement “a = b + c”
        • load B
        • add c
        • store a
    • “register-memory” style
      • At most one of the two given operands can be in memory; one operand (which must be a register) both a source and the destination
      • e.g. to implement “a = b + c”
        • load R1, b
        • add R1, c
        • store R1, a
    • “memory-memory” style
      • three operands, each of which can be in memory or be a register
      • e.g. to implement “a = b + c” : add a, b, c
    • “stack” style
      • Hardware-supported stack instead of registers
      • e.g. to implement “a = b + c”
        • push b
        • push c
        • add
        • pop a
  • Addressing modes
    • Broadly defined, an “addressing mode” is a way of specifying an operand
    • RISC-V addressing modes
      • register
        • e.g. all operands in “add s1, s2, s3”
      • immediate
        • e.g. last operand in “addi s1, s2, 42”
      • base
        • e.g. last operand in “lw s3, 496(s4)”
      • PC-relative
        • e.g. last operand in “bne, s0, s1, xyz”
  • RISC (reduced instruction set computer) vs. CISC (complex instruction set computer)
    • RISC characterized by typical use of:
      • load-store (register-register) style
      • fixed-length instructions
      • limited addressing modes
      • for basic operations, simpler instructions that require less work to accomplish and are more easily pipelined
    • CISC much less well-defined than RISC, but generally:
      • memory-memory, or register-memory
      • variable instruction length
      • many instruction formats, operations, addressing modes
    • RISC overwhelmingly favoured approach now, although Intel x86 architecture lives on …
      • Fast implementations can be achieved by breaking complex “CISC” instructions into RISC-like “micro-ops”
      • However, number of processors used for PCs/servers is dwarfed by the number used for other purposes (smartphones, IoT devices …); here it is claimed that (as of 2019) 99% of 32-bit and 64-bit processors are RISC

  • Fraction field includes only the digits to the right of a binary point

Processor Implementation - Feb 23

The big picture

  • Processor has two main parts:
    • datapath: carries out arithmetic and other operations, moves operands and results around
    • control: selects, activates, sequences activities within the datapath
  • Execution of a machine language instruction is broken up into steps; each step takes a single clock cycle to complete
  • And so, the end of a clock cycle must cause one step to end, and a new step to begin but how?

Sequential circuits - Feb 23

Reference: text Sections A.7, A.8, 4.2

  • Circuits we’ve seen so far have been combinational circuits, whose output is purely a function of the current input
  • The output of sequential circuits depends both on the current input, and on the current circuit “state” (value stored), as set by previous inputs

S-R latch

  • The circuit uses two NOR gates that feed into each other.
  • Inputs:
    • S = Set
    • R = Reset
  • Outputs:
    • Q = stored value
    • Q̅ = opposite of Q
  • Because of the cross-connections, the output of each gate becomes an input to the other. That feedback is what allows the circuit to remember a value.

D latch

  • Basically an S-R latch with extra logic in front so you can control when the stored value is allowed to change.

D flip-flop

  • A D flip-flop stores the value of D at the clock edge and holds it until the next clock edge.

A simple, single clock cycle datapath - Feb 23, 25

Reference: text Sections 4.1, 4.3, 4.4

  • Start with a datapath that can only execute the RISC-V “add”, “sub”, “and”, and “or” instructions (we have designed an ALU that can perform these operations)
    • Step 1: PC (Program counter) holds the address of the current instruction
    • Step 2: PC goes into instruction memory, which returns the instruction stored at that address.
    • Step 3: PC + 4 (next instruction), at the same, the adder adds four to PC, because each instruction is 4 bytes.
    • Step 4: Register file (registers block). If the instruction is add x1, x2, x3, the register file reads x2, x3. Outputs read data 1 = value in x2, read data 2 = value in x3.
    • Step 5: ALU takes the two register values, performs the operation. In previous example, ALU = x2 + x3.
    • Step 6: Write back to register. The ALU result goes back into the register file. example x1 = result. This is controlled by RegWrite = 1.
    • Step 7: Update PC. New PC = PC + 4, whole process repeats for next instruction.
  • Why is this a “single clock cycle” data path?
    • The entire instruction finishes in one clock cycle.
  • For these operation times: memory - 2 ns, ALU - 1 ns, adder - 1ns, register file (read or write) - 0.5 ns, how long would the clock cycle time need to be?
    • The clock must be long enough for the slowest path.
    • Operation times given:
      • memory = 2 ns
        ALU = 1 ns
        adder = 1 ns
        register file = 0.5 ns
    • Total worst-case time:
      • 2 + 0.5 + 1 + 0.5 = 4 ns
    • So the clock cycle must be at least ~4 ns.
  • Why do we need a separate adder, instead of just using the ALU to add 4 to the PC?
    • The ALU is already busy doing the instruction operation.
    • Using a separate adder lets both happen in parallel, which keeps the single-cycle design fast.

  • Need to use one of the inputs to the ALU the immediate operand rather than a second register

      • 0 → read data 2

    • Add new multiplexor, MemtoReg.
      • 0 → ALU result
      • 1 → memory read data

  • For “sw”, need to disable writes into register file

    • PCSrc, add new multiplexor, to choose between PC + 4, plus branch target.
    • Example: beq x5, x6, Label
      • Step 1: fetch instruction. PC goes to instruction memory, instruction is read
      • Step 2: Read registers, instruction tells the register file to read: rs1 = x5, rs2 = x6. So we get read data 1 = x5. Read data 2 = x6.
      • Step 3: ALU compares them. For beq, the ALU usually subtracts x5 - x6. If they are equal, the result is 0. That activates the Zero output from the ALU.

        • Zero = 1 → branch condition true

      • Step 5: Branch target adder computes target. New adder computes PC + branch offset. This is the address of Label.
      • Step 6: PCSrc mux chooses next PC. PCSrc = Branch AND zero.
        • So if instruction is beq, and ALY says the registers are equal, then mux selects branch target.

      • What ALU is doing for beq: ALU compares registers, usually by subtraction.

      • Adder 2: computes PC + branch offset.

Multiple clock cycle datapath - Feb 27

Reference: text Sections 4.5, C.4

  • In a single clock cycle datapath, every instruction gets the same time to complete (one clock cycle), even though less work is required for some instructions than for others
    • e.g., “lw” versus “beq”
  • Will take a brief look at the design of a multiple clock cycle datapath in which:
    • Each instruction is broken up into multiple steps, with instructions requiring more work using more steps
    • Instructions are executed one-by-one (as in the single clock cycle data path) i.e. no pipelining
  • How should instructions be broken up into multiple steps?
    • Ideally, the work done in each step should take similar amounts of time to complete — since each step will be given the same time, one clock cycle!
  • All would have the same first two steps:
    1. Fetch the instruction and in parallel increment PC
    1. Fetch register operands and in parallel decode the instruction
  • One possible breakdown into steps for our subset of RISC-V instructions (a simple breakdown, but likely not ideal with respect to balancing work in each step)
  • Subsequent steps would depend on the instruction type, e.g. for “lw”, could use three more steps:
    1. Calculate memory address
    1. Read from the data memory
    1. Write into the register file
  • While for “beq”, e.g., could use just one more step in which the branch target address and in parallel the register operands are compared.
  • Additional storage units will be needed to save the work we’ve done in one step for use in the next … for example,. we will need an Instruction register to hold the instruction fetched in step 1

Pipelining - Feb 27, March 2, 4, 11

Reference: text Sections 4.6-4.11

  • Idea is to overlap the processing of different instructions, like in an assembly line

Potential performance improvement with pipelining

  • Consider IPC (”instructions completed per clock cycle”)
  • Single clock cycle datapath has IPC = 1, but needs very long clock cycle time
  • Multiple clock cycle datapath can have much shorter clock cycle time (therefore much higher clock rate), but has much lower IPC
  • Pipelined datapath can potentially get close to IPC = 1 (but not quite, owing to “hazards” that disrupt pipeline operation) with short clock cycle time (high clock rate)

Pipeline stages for RISC-V Subset

  • The work done in each step of instruction execution should take similar time to complete — since each step will be given the same time, one clock cycle
  • For our RISC-V subset, use following five steps and corresponding pipeline stages (a simple breakdown, but likely not ideal with respect to balancing work in each step)
    • IF: instruction fetch and update of PC
    • ID: instruction decode and register reads
    • EX: execution, address calculation
    • MEM: memory access, branch completion
    • WB: write back into register file
  • Note that all instructions go through the same 5 pipeline stages … but what happens in 3rd through 5th stages is dependent on instruction type.
  • Pipelined datapath design for RISC-V subset divide our single clock cycle datapath into five pieces, corresponding to our five stages of instruction execution
  • … but will need to add pipeline registers to hold the results of one stage of execution, for use in the next tage
    • Registers named IF/ID, ID/EX, EX/MEM, and MEM/WB

Initial Design

  • Each pipeline register must be large enough to hold everything subsequent stages might need (including control signals, as we’ll see shortly)
  • e.g., for “sw s0, 4(s1)”, what happens in each stage?
    • IF (first clock cycle of execution) — PC is used to fetch instruction and store in IF/ID pipeline register.
      • What gets stored: Instruction = sw s0, 4(s1), PC + 4
    • ID (second clock cycle) — Decode instruction fields, read registers
      • For sw s0, 4(s1)
      • rs1 = s1 → base address
      • rs2 = s0 → value to store
      • immediate = 4
      • Register file outputs:
        • Read data 1 = value of s1
        • Read data 2 = value of s0
        • Imm Gen = 4
      • Pipeline register must store: ALU control signals and MemWrite = 1
    • EX (third clock cycle) — ALU computes memory address: address = s1 + 4
      • ALUSrc = 1 → uses immediate
      • What gets passed to MEM stage:
        • ALU result (address)
        • value of s0 (data to store)
        • MemWrite = 1
    • MEM (fourth clock cycle) — Memory[address] = s0
      • Address comes from ALU
      • Write data comes from s0
      • MemWrite = 1
    • WB (fifth clock cycle) — nothing, b/c sw does not write to a register, so RegWrite = 0

Dynamic branch prediction

  • Most popular approach to branch hazards
    • Actually a “must” with the current “multiple issue” datapaths
  • Keep some history of previous branch instruction outcomes; use history for prediction
    • Complex schemes of this sort have been made feasible by increases in the number of transistors possible per chip (Moore’s law)

A “1 bit” dynamic branch prediction scheme

  • Record history in a “branch prediction buffer”, implemented on the processor chip
    • Organized as an array indexed by bits from the branch instruction address
    • Each array element is just a single bit
    • Whenever a branch instruction is executed, store a “1” in corresponding array element if the branch was taken, and a “0” if not
  • When a branch instruction is executed, predict the outcome (”taken” if “not taken”) to be the same as the previous outcome
    • …except, it’s possible that a different branch instruction was recently executed that uses the same entry in the branch prediction buffer!
  • Implement “taken” predictions using a “branch target buffer”
    • Caches branch target addresses and possibly as well as the instructions at these addresses

More complex dynamic branch prediction schemes

  • If store more history information, can (usually) make more accurate predictions!~
  • For branches that are usually taken but occasionally are not taken (or vice versa) about 1/2 as many wrong predictions as the “1 bit scheme”
  • Much more complex schemes are often used in practice, e.g. “neural network” based
  • Such schemes are able to achieve high branch prediction accuracies (> 95% accurate)

Exceptions

  • Events that cause the execution of the currently running program to be stopped and operating system code to run
    • Application program may or may not be resumed later, depending ont he nature of the exception
  • Three basic types
    • Internally generated, unexpected events
    • Externally generated events (”interrupts”)
    • System calls

System calls result from execution of a system call instruction (e.g., the “ecall” instruction in RISC-V)

  • Purpose is to make a request to the operating system to perform some service
  • Can’t use an ordinary procedure call, since transition to the operating system code must be made concurrently with a change to the privilege level (”mode”)

Basic approach to handling exceptions

  • Instructions prior to an instruction causing an exception allowed to complete, others flushed
  • Start fetching instructions from the exception handler in the operating system … In RISC-V systems, go to same fixed memory address for all exception types (alternative approach called “vectored interrupts”)
  • In RISC-V, how does the exception handler know what type of exception has occurred?
    • Numeric code indicating the exception type is stored by the hardware in the SCAUSE (”supervisor exception cause”) register
  • Also may need to know where we were in the application program when the exception occurred … in RISC-V systems the relevant instruction address is stored by the hardware in the SEPC (”supervisor exception program counter”) register

Beyond simple pipelining

  • How can we achieve higher performance than possible with just the simple pipelining we’ve looked at so far?

Deep Pipelining (also called “super-pipelining”)

  • Break up instruction processing into a greater number of steps
  • Current common processors typically have pipelines with 10-20 stages for integer operations

Superscalar (also called: “dynamic multiple issue”)

  • With this approach, start (”issue”) multiple instructions per clock cycle
  • Up to hardware to check for data hazards
  • Not all components of pipeline replicated to the same degree, so must also deal with the possibility of structural hazards

Out-of-order execution (”dynamic pipeline scheduling”)

  • Allow instructions to execute out of order, so that an instruction that takes longer to process does not hold up all the instructions behind it
  • Although can execute out of order, do require in-order commit

Speculation

  • Superscalar, out-of-order execution processors make heavy use of speculation, including both branch prediction, and load address speculation
  • Example code for load address speculation:
    • sw t1, 100(s0)
    • lw t2, 4(s2)
  • Can the “lw” be executed before the “sw”?

VLIW (”very long instruction word”, also called “static multiple issue”)

  • Like superscalar / dynamic multiple issue approach, multiple instructions issued per clock cycle
  • But with this approach, it’s the compiler’s responsibility to group together independent instructions to be issued together
  • Motivation is simpler hardware, but approach is less popular than dynamic multiple issue approach

Security implications of speculation and out-of-order execution

  • Security attacks made possible by speculation and out-of-order execution have been discovered (Meltdown, Spectre)
  • Speculation and out-of-order execution do not change the functional results of code execution
    • For example, if an attempt to read protected info should generate an exception, it will still generate an exception if using speculation and out-of-order execution
  • Speculation and out-of-order execution may, however, change the microarchitecture state (e.g. contents of caches) resulting from code execution
  • Can these changes to microarchitecture state be made to depend on protected info?
    • If so, then may be possible to use timing attacks to reveal info
  • A number of mitigations have been implemented, e.g. KPTI, but completely addressing these vulnerabilities may require substantial system design changes

Performance Limitations

  • Deep pipelining, superscalar, out-of-order execution, speculation, VLIW … all these techniques exploit ILP (”instruction level parallelism”) in ordinary sequential programs
  • Unfortunately, experience has shown that the amounts of ILP we can exploit when executing common software applications are quite limited.
  • Further improving performance requires software written to explicitly exploit parallelism.
  • At the hardware level, multiple approaches to supporting parallel execution, including: multicore processors, vector instructions, GPUs, accelerators
  • Software is written to exploit these hardware capabilities, e.g. using multi-threaded programs, compiler support, language extensions, libraries.
  • Will take a brief look at parallel computing, time permitting, as our last topic in the course …

Memory

  • Would like to have a computer memory that is both very large and very fast … but there’s a fundamental tradeoff between size and speed
  • Solution is to use multiple components of varying sizes and speeds, in a way that (ideally!) achieves the benefits of both high speed and large size
  • For this purpose, implement the “memory space” abstraction in machine/assembly language using a memory hierarchy, consisting of:
    • Processor cache memory (fastest but smallest, implemented in SRAM
    • Main memory (DRAM)
    • Secondary memory (magnetic disk, SSD, … large but relatively very slow)
  • SRAM implemented using flip-flop type circuits, typically 6 transistors per bit; data retained as long as power is on
  • DRAM much less area per bit (one capacitor, one transistor) but slower access time; use periodic “refresh” to retain data

Processor caches — Mar 11, 13, 16

Reference: text Sections 5.1-5.4, 5.8

  • Commonly have multiple levels of processor cache
    • Primary (or “level 1”) cache, typically split into separate instruction and data caches (e.g., 32 “KiB” each)
    • Secondary (or “level 2”) cache, larger but slower than primary cache (e.g., 2 “MiB”)
    • Tertiary (or “level 3”) cache, larger but slower than secondary cache
    • (Typically, single L3 cache shred among all cores on same chip, while each core has own L1 and L2 caches)

Processor cache management

  • In general purpose processors, caches are managed by the hardware (”transparently” to application software)
  • What is put in cache memory?
    • Copies of main memory words that are likely to be needed in near future
  • How are cache memory contents accessed?
    • On every memory operation, hardware looks in cache memory first, to see if there’s a copy there, using as the “lookup key” the main memory address

Locality of reference

  • How does the hardware determine what memory words are “likely to be needed in near future?”
  • Most programs exhibit locality of reference:
    • “temporal locality”: words recently accessed are likely to be accessed again in near future
    • “spatial locality”: words adjacent in main memory to words recently accessed are likely to be accessed in near future
  • What are some common program features that would lead to temporal or spatial locality?

Operation for memory reads

  • Hardware looks in primary (level 1) cache first
    • if “hit”, done!
    • if “miss”, look in the next level(s) of cache … if in none of these, read from main memory
  • When have the data, place a copy in the cache(s) … likely a good decision, if there is temporal locality
  • (some details here regarding operation with multiple levels of caches, e.g. “inclusive”, “exclusive”, neither, …)

Blocks

  • On a miss, hardware retrieves more than just the requested word … also retrieve some words adjacent to it in main memory
  • Likely a good decision, if there is spatial locality
    • (time to retrieve N words) <<

      N x (time to retrieve one word)

      and so if we do need these other words in near future, better to get them now!

  • Exactly which other words do we get?
  • Statically divide main memory into fixed-size blocks (also called lines), retrieve entire block containing requested word
  • e.g., for block size of 4 words:
    • block 0: words with addresses 0, 4, 8, 12
    • block 1: words with addresses 16, 20, 24, 28
    • block 2: words with addresses 32, 36, 40, 44
    • …
  • If requested word with address 20, retrieve block 1

Operation for memory writes

  • Hardware looks in primary (level 1) cache first
  • If “hit”, two options:
    • write-through policy: copy in cache is updated, and the write is propagated to the next level
    • write-back policy: only update copy in cache
  • With the write-back policy, when a “dirty” block is removed from cache, must “write back” the updated contents
  • If “miss”, two options:
    • Propagate the write to the next level
    • Write-allocate: read entire block containing word, and then update (in the cached copy) the particular word being written to
  • When need to write to lower-level cache or to main memory, don’t need to wait for the write to complete! … instead, just put in write buffer …

Cache Performance Metrics

  • Hit latency: Time it takes to look in the cache and retrieve the requested data when get cache hit
    • e.g. often 3 or 4 clock cycles for primary caches
  • Miss rate: Fraction of memory references not found in the cache
    • Miss rates of under 5% are common for primary caches, under 2% for primary/secondary cache combination
  • Miss penalty: Time required for a block to be retrieved from the next level
    • Note that typically have very large miss penalty if have to go to main memory, could be multiple hundreds of clock cycles

Processor Cache Organization — Mar 16, 18

  • Will look first at the simplest organization, called direct mapped, then will look at a closely related organization called set associative

Direct-mapped cache

  • A big array (or table); at each position (row), store the contents of a single memory block, as well as:
    • Some status bits
    • A tag field that specifies which memory block has been stored there.
  • When a copy of a memory block is put in the cache, what position is used?
    • When memory block number i is copied into a direct-mapped cache with M positions, it is put in position i mod M
    • Since each position has space for just a single block, the new block will replace whatever memory block was there before
  • Use of tag field
    • Any block that would be put in position j (0 ≤ j ≤ M) in the cache has a block number that gives a remainder of j when divided by M
    • … and so the tag field at each position j need only store the integer part when the block number is divided by M

Direct-mapped cache example

  • To make example simpler, consider a cache much smaller than those in practice, with just M = 16 positions
  • Assume a block size B of 32 bytes (or 8 words), and suppose do reads (e.g. “lw”) on the following memory addresses: 80, 1040, 948, 1864, 836
  • What memory blocks get put in the cache, and where, and what are the final cache contents?

Using fields from memory address to determine memory block number, cache position, and tag field

  • Simple if M, B chosen as powers of 2: M = 2^m. B = 2^b
  • Rightmost b bits of memory address give the relative position of the byte with that address within its memory block
  • Remaining 32 - b bits give the memory block #
  • Rightmost m bits of the memory block number give the cache position that the block would be put in
  • Remaining (32 - b) -m bits give the tag field value

Advantages/disadvantages of direct-mapped cache

  • Advantage: fast access
  • Disadvantage: no choice of which block to replace (can lead to bad performance if “unlucky”)

Set-associate cache

  • In each row (termed a “set”) have storage spaces for multiple memory blocks
  • If M sets, storage spaces for E memory blocks per set, can store M x E memory blocks in total
    • E = 1 gives direct-mapped cache
      • E = memory blocks per set
    • M = 1 gives “fully associative” cache
      • M = sets
    • Common values for E range from 2 to 32
  • When a copy of a memory block is put in the cache, where can it be put?
    • Memory block number i can be put in any of the storage spaces in set i mod M

Replacement policies for a set-associative cache

  • Options include:
    • (pseudo) random
    • LRU (”least recently used”)
    • approximate LRU
  • LRU motivated by temporal locality … blocks recently accessed are likely to be accessed again soon and should be kept in cache
  • Approximate LRU motivated by the cost of true LRU for large E

Access time for a set associative cache?

  • When doing a lookup to see if cache contains memory block i, check in set i mod M, similarly as for a direct-mapped cache
  • Now, however, need to check multiple tag fields (specifically, E tag fields)
  • Comparisons with the tag field value that would be used for memory block i can be done in parallel

Set-associative cache example

  • As in previous example, suppose do reads on the following memory addresses: 80, 1040, 948, 1864, 836, and suppose the block size B = 32 bytes.
  • Consider cache that can store same total memory blocks as the direct-mapped cache in previous example, but now with M = 8, and E = 2.
  • Set = block number mod E

Final cache contents

  • Assuming an LRU replacement policy, memory blocks 32, 29, 58, 26 (not memory block 2)
  • Suppose now we read the memory address 1888, will we get a cache hit or cache miss?
    • Cache miss, because block size B = 32, so first find memory block for 1888.
      • 1888/32 = 59.
    • M = 8 sets, set number = 59 mod 8 = 3.
    • Tag = [59/8] = 7.
    • So we need to look in set 3 for a block with tag 7.
    • Blocks in cache are 32, 29, 58, and 26.
    • Their sets are: 32 → set 0, 29 → set 5, 58 → set 2, 26 → set 2.
    • There is nothing in set 3, and block 59 is not in the cache

Design choices for processor caches

  • Must decide:
    • Number of levels of cache
    • Size of each cache
    • Memory block size (often the same for all levels of cache, but sometimes different)
    • Associativity of each cache and replacement policy if set associative
  • Various tradeoffs to consider… for example, suppose fix the total # of bytes cache can store, and consider the choice of memory block size

Virtual Memory Addressing — Mar 18, 20, 23

(reference: text Section 5.7)

  • In machine/assembly language, use the abstraction of a memory space … how can we implement this abstraction?
    • If knew what main memory locations our program code and data will occupy, when executable is created, our memory space abstraction could correspond directly to the hardware main memory
    • Commonly, however, when executable is created, the main memory locations the program will occupy when it is loaded into memory and run are unknown!
  • With virtual memory addressing, we can use any memory space addresses we want when creating an executable (although, in practice, will use conventions) … these addresses termed virtual addresses
  • … at run time, these virtual addresses are translated into actual main memory addresses (called “physical addresses”), according to where in main memory our code and data actually reside

Benefits of virtual memory addressing

  • Ease of use
    • Memory space abstraction provides illusion of a large & private memory
    • Actual location of program in main memory need not be determined until program is run
    • Program need not be stored contiguously, and can be moved during execution
  • Protection
    • Not possible for a program to access a part of main memory that does not belong to it
    • Crucial mechanism for allowing multiple applications to safely share a machine
  • Facilitates use of disk as backing store
    • Can run a very large program that doesn’t completely fit in main memory
    • Can run a number of programs concurrently even if they don’t all completely fit

Overview of virtual memory address translation

  • Divide virtual address space (range of possible memory addresses in machine/assembly language memory space abstraction, in RISC-V RV32I, 0 to 2^32 -1) into “virtual pages”
    • e.g., with 4 KiB (=4 x 2^10 = 4096 byte) pages:
  • The portion of an executable that has been assigned the addresses of a virtual page i is referred to as virtual page i of that executable
  • Divide main memory into “physical pages” of the same size as virtual pages
  • When a program is loaded into memory, each of its virtual pages can be placed in any physical page
  • Operating system maintains a page table for each process (program in execution) that records, for each of the virtual pages of the process, which physical page (if any) it has been placed in
  • A simple page table organization:
    • One entry for each virtual page in the virtual address space
    • Use virtual page number to index into table
    • Each entry i contains some status bits, and (for a valid entry) the number of the physical page into which virtual page i has been loaded
    • e.g.:
  • Suppose page size if 4 KiB, what physical address should virtual address 8376 be translated into?

Manual address translation — Computing one specific address

  • Step 1: which virtual page is this?
    • VPN given by integer part of 8376 / 4096 (2) (the remainder (184) gives the offset of this address within its virtual page)
      • Divided by 4096 → gives VPN
      • Remainder → gives offset
  • Step 2: which physical page has this virtual page been put in?
    • Use VPN to index into page table, finding that virtual page 2 has been put in physical page 5
  • Step 3: add offset to starting address of physical page, giving 4096 x 5 + 184 = 20664
    • Physical Address=(PPN × page size)+offset

How big can physical memory be?

  • Use bit counts
  • PPN bits + offset bits → used for maximum memory size
    • Offset calculated by: virtual address bits - virtual page # bits
      • e.g. for virtual page # = 44 bits, virtual address = 57 bits, 2^57 - 2^44 = 2^13
      • if PPN = 38 bits, answer is 2^38 + 2^13 = 2^51

Hardware address translation

  • VPN and offset can be found by extracting fields of the virtual memory address
    • e.g., with 4 KiB = 2^12 byte pages, rightmost 12 bits give the offset, rest of the bits give the VPN
  • Hardware uses the VPN to index into the page table, and then replaces the VPN with the physical page #

Protection and sharing

  • Ability to create, change page tables restricted to OS (how?)
    • Through hardware privilege levels (user mode vs kernel mode)
    • Only OS (kernel mode) can: create/modify page tables, change mappings. User programs cannot directly access page tables.
  • Status bits can include one or more bits that control the types of allowed access (writeable? executable?)
    • read/write/execute bits
    • valid bits
  • Possible to share physical pages (how? what use cases?)
    • Different processes’ page tables map to the same PPN
    • Why useful?
      • Shared libraries (e.g. one copy of libc for all programs)
      • Fork (copy-on-write): parent + child share memory until one writes
      • Inter-process communication

Making address translation fast

  • The problem: Page tables are stored in main memory, main memory is very slow, address translation needed for every instruction fetch and every load/store.
  • The solution: Use cache(s) for page table entries on the processor chip, called TLBS (”translation-lookaside buffers”)
  • Each entry in a TLB includes:
    • A tag field that specifies which virtual page this entry is for (extracted from the VPN)
    • A page table entry (status bits plus a physical page number)
    • In some systems, a PID or ASID (if don’t have, OS has to flush TLB on every process switch)
  • How it works:
    1. CPU generates virtual address
    1. TLB lookup:
      1. hit → get PPN immediately (fast)
      1. miss → go to page table in memory, then update TLB
  • Typically have separate instruction and data primary (level 1) TLBs, as well as a secondary (level 2) TLB
  • TLBs much smaller than processor caches, yet very small miss rates (typically less than 1%) (why?)
    • B/c of locality: programs reuse the same pages a lot, and loops/stacks/functions → same few pages repeatedly

Should processor cache lookups use virtual or physical memory addresses?

  • Problem with using virtual addresses is that each process has own mapping to physical addresses
    • … but for primary caches, there’s also a problem with using physical addresses … lookup for primary caches must be very fast!

Possible events when attempt to read memory (e.g., “lw” or instruction fetch)

  • If hit in TLB:
    • can get translation into physical address from TLB, proceed w/ cache lookup(s)
  • If miss in TLB:
    • Need to access page table of the running process, load page table entry into TLB, and then restart the read operation
    • In some systems hardware handles, in other systems exception generated and OS handles
  • If miss in TLB and there is no valid page table entry
    • Termed a page fault … must be handled by OS
    • Invalid address? … if so, application terminated
    • Valid address but page not yet loaded in memory? … if so, OS initiates I/O to read page in from disk … when I/O finally (!) completes, OS updates page table and marks process as being runnable again

Page replacement

  • To make room for new pages that are brought into memory when page faults occur, the operating system will need to sometimes remove pages
  • If a page to be replaced is dirty (and the page is not “file-backed”), written to swap space on disk
    • Can use one of the page table status bits to record whether dirty or not
  • OS needs to be able to do the inverse mapping to that done by a page table
    • given a physical page that OS wants to replace the contents of, what virtual pages are mapped to it?
    • OS needs to invalidate page table entries for removed pages and any copies of these in TLB (how?)
  • Pages that are good candidates for replacement are identified proactively
  • … then, if a page replacement is needed, will have already identified some good choices

Page replacement policies

  • Typically operating system uses some approximation to LRU
  • e.g. “clock” algorithm (simplest variant):
    • Each page table entry includes a “reference” (or “use”) bit
    • OS scans the physical pages at some steady rate, setting use bits of corresponding page table entries (how found?) to 0
    • If when OS scan reaches a page the corresponding bit is already 0, page is good candidate for replacement!

Page table size

  • The problem: page tables too big if have one entry for each virtual page in the virtual address space
    • Many processors now support 57-bit virtual addresses (up from 48-bit) and 4 KiB = 2^12 byte pages
    • Virtual address space then has 2^57 / 2^12 = 2^45 virtual pages … if one 8-byte PTE for each virtual page, get 2^45 x 8 bytes = 256 TiB for a single page table
  • One solution: Maintain bounds on the ranges of virtual addresses in use, only have page table entries for addresses within bounds
  • More flexible solution: Multiple levels of page table, only allocate pieces you actually use
    • e.g. suppose 30-bit virtual addresses, 4 KiB pages
      • Divide the virtual pages into “clusters” of 512 (2^9) consecutive pages each

      | 9 bits | 9 bits | 12 bits |
      | root | leaf | offset |

      • Bits 0-11 give which byte within page, bits 12-20 which page within page cluster, bits 21-29 which cluster
      • bits 21-29 used to index into a “root” page table with 215 (2^9) entries giving the physical page numbers of “leaf” page tables
      • bits 12-20 index into a “leaf” page table, each has 512 entries giving physical page numbers for virtual pages
      • if each entry 8 bytes, each table fits in one 4 KiB page
      • at most 512 leaf page tables … only need to allocate a particular leaf table if process is using at least one page from that part of the virtual address space
  • With each additional level of tables, can increase virtual address size by 9 bits (how many levels needed for 57-bit addresses?)
    • Follow the pattern:
      • offset = 12 bits
      • remaining = 57-12=45 bits
      • each level handles 9 bits
      • So: 45/9 = 5
  • Neat feature: can support a mix of page sizes (e.g. 4 KiB, 2 MiB = 512 x 4 KiB); e.g., in two-level scheme, a “root” page table entry could (optionally) give a starting PPN for whole cluster

(System) Virtual Machines — Mar 23

(reference: text Section 5.6)

  • Idea to use a VMM (”virtual machine monitor” or “hypervisor”) to support sharing of the resources of a computer among a number of VMs (”virtual machines”)
  • Each VM includes its own OS, and presents to its users the illusion of having an entire computer to themselves
  • …motivation? Can run multiple unrelated applications/services on the same computer, even if they need different OSes, with improved fault isolation and security
  • Use cases include:
    • server consolidation (replacing multiple servers by a single server)
    • cloud computing, IaaS (”Infrastructure as a Service”)
    • … and other scenarios where one wants strong fault isolation / security

Implementing the VM idea

  • Only the VMM must be allowed direct access to shared system recourses, such as I/O devices
  • In systems w/o VMs:
    • application programs run in “user mode”
    • OS runs in “kernel” (”supervisor”) mode
  • In systems w/ VMs, one approach is to run both the OS of each VM (a “guest OS”) and the applications in user mode, and the VMM in kernel mode
  • Idea is that when a guest OS attempts a privileged operation, an exception will occur, causing the VMM to be invoked … but some pitfalls:
    • Some architectures have cases where don’t get exception
    • Can be substantial performance cost
  • How to address pitfalls in this approach?
    • In “full paravirtualization”, modifications are made to guest OSes to directly request services from VMM
    • Hardware support for virtualization (e.g., new mode, “nested paging”, new instructions,…)
  • Typically: use hardware support, with paravirtualized drivers (rest of guest unmodified) (e.g., KVM-QEMU) or SR-IOV for I/O

Coherence and Consistency — Mar 25

(reference: text Section 5.10)

  • In multiprocessor systems need to ensure that the memory system provides coherence and consistency for parallel programs

Coherence

  • Essentially, results of executing a parallel program should be the same as if there was just one main memory and no caches
    • Constrains possible results from accesses to a single memory block

Consistency

  • With the strongest type of consistency (”sequential consistency”), the results of executing a parallel program must be the same as an execution in which operations occur sequentially in some order consistent with program order
    • … but commonly processors implement a slightly weaker notion of consistency
  • How can we ensure sequentially consistent behaviour, when needed, for parallel programs?
    • … instruction set support, e.g. “fence” instruction, “aq”/”rl” options, in RISC-V

Implementing coherence

  • Can achieve coherence if:
    • On a read miss at a processor, if the required memory block is dirty in another processor’s cache, get the updated memory block
    • When write to a memory block, first read block into cache if not present (getting updated copy if dirty in another cache), and then invalidate all copies in the caches of other processors

MESI (”Modified, Exclusive, Shared, Invalid”) cache coherence protocol (one of a # of such protocols)

  • Four possible states for a “line” (memory block in our terminology) at the cache of a particular processor core
  • Modified state: only this cache has a copy, which is dirty
  • Exclusive state: only this cache has a copy, which is clean
  • Shared state: has clean copy, may also be in other caches
  • Invalid state: invalidated or not present
  • Given these four states, what state transitions occur on local and remote reads and writes?
  • Hmm … suppose read miss, for example … how does the core at which the miss occurred know where to get the data from?

Two basic implementation approaches: snooping protocols (simpler) and directory protocols (more scalable) (”snoop filters” are hybrid approaches)

  • Snooping protocols
    • On a read miss at a core, broadcast a message that will be seen by all cores
    • When write, may similarly need to broadcast
  • Directory protocols
    • Use a directory, implemented in hardware, to keep track of the caching status of each block … now can consult the directory to determine exactly where messages need to be sent

False sharing

  • Occurs when threads running on different cores are reading & writing different variables that happen to occupy the same memory block
  • False sharing can greatly hurt performance (…why?)

I/O — Mar 25, 27

(reference: text Sections 5.2, 5.11)

Wide variety of I/O devices

  • Storage devices such as magnetic disks, SSDs, USB flash drives, …
  • “input” and/or “output” devices that facilitate communication w/ users and other machines

Performing I/O

  • Service provided by OS (operating system provides protected sharing, handles low-level details)
  • Three basic approaches:
    • polling: processor initiates or enables I/O operation, then periodically asks I/O device “are you done yet?”
    • interrupt-drive I/O: processor initiates or enables I/O, I/O device interrupts processor when I/O operation completed
    • DMA (”direct memory access”): like interrupt-driven I/O, except that DMA controller is able to directly transfer data to/from memory

For communication between OS and I/O devices, two alternatives:

  • Special machine language instructions
  • Memory-mapped I/O: dedicate a portion of the physical address space to registers within the I/O device controllers, and access using ordinary load and store instructions.
    • Example: reading a character form a simple keyboard device with a control/status register and a data register, using polling in a “busy-wait” loop
      • Control/status register: includes a “ready bit” that is set to 1 by device controller when new character is typed (assume here all other bits read as 0)
      • Data register: when new character typed, put in this register by device controller

Hard disk drives (magnetic disks)

  • Consist of 1-4 platters, each side of which can be used for recording data (by magnetizing spots on surface)
  • Disk “arm” has one read/write head per surface
  • Each surface divided into tracks, and each track is divided into sectors (4 KiB sector size)
  • Three major components of disk access time:
    • Seek time: time to move arm to the required track (e.g., could be >20 ms for a “long” seek, with avg 3-4 ms)
    • Rotational latency: time until first sector of data to be read/written rotates under the read/write head (e.g., for a 10,000 RPM disk, what would average rotational latency be?)
    • Transfer time: time from when the first bit is read/written until last bit is read/written (e.g., for 200 MB/sec transfer rate, what is time for 4KB?)
  • Operating systems typically will read/write multiple sectors at once if possible (…why?)
  • Caching is used, both within the disk drive itself, and in main memory

SSDs (”solid-state drives”)

  • Use integrated circuit technology for data storage, and so no moving parts, but like magnetic disk data is retained when powered off
  • Commonly, based on NAND flash memory (different types, SLC, MLC, TLC, QLC)
  • Flash chips organized into banks (or “planes”), each with many erase blocks (e.g., each 16 MiB), each of which consists of many pages (e.g., each 16 KiB)
  • Before writing to (”programming”) an individual page, entire block must be erased (takes a few ms!)
  • After many repeated program/erase cycles, storage cells wear out and becomes unusable
  • How to get an SSD from a collection of flash chips?
    • Can use same block-based interface to rest of system as a hard disk drive
    • Flash translation layer handles mapping to bank/erase block/page, erase operations, “wear levelling”, …
  • Cost, speed, typical capacity intermediate b/t disk & main memory, power usage lower than both
  • Historically, dramatic reductions in storage costs!

RAID (”redundant arrays of inexpensive disks”)

  • Goal is to improve reliability of hard disk storage system, as well as performance and cost
    • Annual failure rate (AFR) for the disks in large data centers > 1%
    • When a disk failure occurs, would like to remain fully operation w/ no interruption in service, no data loss
    • Would also like to improve performance, lower cost, by exploiting parallelism
    • Would like benefits to be achieved transparently (a RAID system can be used as if it was just a single big disk)
  • Multiple variants of RAID
    • RAID 0: uses “striping” w/ no redundancy, and so really just “AID”
      • e.g. w/ 2 disks:
        • “block 0 allocated on disk 0
        • block 1 allocated on disk 1
        • block 2 allocated on disk 0
        • block 3 allocated on disk 1
        • …
        • dependability worse, how abt performance?
    • RAID 1: uses mirroring
      • Dependability? Performance? Cost?
    • RAID 2: unused
    • RAID 3, 4: relatively uncommon
    • RAID 5: uses “distributed block-interleaved parity”
      • If would need N disks w/o RAID, then with RAID 5, would use N+1 disks to make a “RAID group”
      • Blocks striped across disks, with a “parity block” added to every N data blcoks
      • W/ “even parity” variant of scheme, each bit in parity block chosen such that number of ones in that bit position across all N+1 blocks is even (use XOR)
      • Relative positioning of parity block is cycled
      • Suppose failure results in a data block being unreadable … how can block contents be recovered?
      • A disadvantage is extra cost when writing a single data block (overhead much less for large writes)
    • RAID 6: similar idea as RAID 5, but two extra disks, better protection against disk failure
      • Two “redundancy” blocks P and Q added to every N data blocks, even if two of the N + 2 blocks can’t be read, able to recover (extra cost for small writes?)
      • Has become common owing to steadily increasing disk sizes, time to rebuild contents of a failed disk
  • Also possible to combine RAID variants (”nested RAID”)

Parallel computing: beyond ILP — Mar 30, Apr 1, 6

(reference: text Sections 6.1-6.8, 2.11, 3.6, 3.7)

  • Want greater parallel execution than possible when exploiting only ILP (”instruction level parallelism”) in a single sequential program, one a single processor
  • Two basic questions:
    • what can be executed in parallel?
    • how best to achieve this parallel execution?

What can be executed in parallel?

Different applications

  • Easy, but parallelism limited by the number of applications want to run at the same time

Processing of different requests to a server application

  • e.g., Google search
  • Parallel execution opportunities abundant if high request rate, but doesn’t speed up the processing of any single request

Different computations within a single application

  • Exploit functional parallelism
  • e.g., pipeline of threads, each implementing a different function
  • Typically, however, don’t have many different computations that can run concurrently

Same computation but on different data elements

  • Exploit data parallelism
  • Different ways this type of parallelism can be expressed
    • e.g., programmer might create multiple threads for operating concurrently on the different blocks of a big array
    • e.g., programmer might use a single “vector instruction” to carry out the pairwise addition of the elements of two big vectors
  • In many important applications (e.g., machine learning) ample opportunities for exploiting large scale data parallelism, enabling highly-parallel execution

How to achieve parallel execution?

Clusters

  • Collection of computers connected using LAN
    • Commonly use rack-based configuration, in which each computer is “pizza box” sized and fits together w/ tens of other such computers in a standard rack frame; may have many such racks
  • Communication is by message passing (e.g. using MPI)
  • Messages not only serve to communicate data, but also result in synchronization (”receive” will block until a matching “send”)

Grids

  • Computers may be geographically distributed
  • e.g., “volunteer computing” projects (SETI@home, BOINC middleware, …)
  • Message passing much more expensive when have to traverse wide-area networks, but grids can be effective for “embarrassingly parallel” applications

Shared Memory Multiprocessors & Multicores

  • Shared physical main memory
    • UMA (”uniform memory access”): access to any word of physical main memory takes about the same amount of time
    • NUMA (”nonuniform memory access”): main memory implemented in multiple components distributed among processors, accessing “close” memory is much faster
    • NUMA systems more scalable, but also more complex for programmer trying to optimize performance
  • Programmer can use operations on shared memory locations for thread communication, data sharing
    • … but often will need to synchronize accesses to shared data structures to avoid corruption
  • For synchronization, programmer can use constructs provided by programming language and/or libraries
    • … but how are these synchronization constructs implemented in machine/assembly language?

Hardware Multithreading

  • Within a single core, replicate some components to support execution of multiple threads
  • Three types:
    • Coarse-grained multithreading: when a thread stalls, switch to a different thread … replicate hardware resources such as the register file, PC so that each of the threads alternating execution have their own
    • Fine-grained multithreading: switch every clock cycle!
    • Simultaneous multithreading (called “hyper-threading” by Intel): instructions from multiple (typically two) threads can be issued in the same clock cycle … exploits techniques such as “register renaming”

Vector architectures, instruction set extensions

  • Variety of designs that exploit data parallelism using some interpretation of “SIMD” to speed-up operations on vectors of data
    • Flynn’s taxonomy classifying computer architectures:
    • “SISD” (”single instruction stream, single data stream”) i.e. conventional uniprocessors
    • “MIMD” (”multiple instruction stream, multiple data stream”) i.e. multiprocessors
    • “SIMD” (”single instruction stream, multiple data stream”)
    • “MISD” (unused)
  • Vector instruction set extensions in x86
    • MMX (”MultiMedia eXtension”), SSE (”Streaming SIMD Extensions”), SSE2, AVX (”Advanced Vector Extensions”), AVX2, AVX-512, AVX10, …
    • Use large registers (e.g., 512 bits in AVX-512) that can each store a short vector of operands (e.g., in AVX-512, 16 single precision floating point values)
    • Instructions provided for operations on these vectors (e.g., single instruction can do pair-wise addition of two vectors each with 16-floating point values)
    • AMX (”Advanced Matrix Extensions”) extends idea to matrices (have 2-d registers called tiles) … important application domain is deep-learning training & inference

GPUS (”graphics processing units”)

  • Originated from merging of specialized hardware units used for graphics
  • Now used for many other computationally-intensive applications (since GenAI, NVIDIA GPUs, e.g., in exceptionally high demand … 10yr stock return Feb 2016-2026 > 24000%!)
  • Exploit data parallelism
  • Representative high-level design:
    • GPU has multiple multithreaded SIMD processors
    • Each SIMD processor has multiple ALUs that execute identical instructions (on different data) in lock-step
    • Block scheduler assigns blocks of threads to the SIMD processors; thread scheduler within each SIMD processor can use fine-grained multithreading idea

Specialized processing accelerators

  • Targeted at particular applications such as image and video processing, machine learning, …
  • Accelerators for AI applications, sometimes termed “neural processing units” (NPUs), have become widely used
    • Found in smartphones, personal computers, cloud computing systems,…
    • an example is Google’s “tensor processing unit” (TPU) (7th gen TPU (”Ironwood”) announced last year)
  • TPUv1
    • Specialized for matrix processing (as needed for neural networking training/inference …)
    • Matrix multiply unit contains array of 256 x 256 (65, 536) multiply-accumulators … SIMD parallelism !
    • Dedicated memories
    • Smaller data types (8 and 16 bit integers)
    • Power efficient … included architectural units and features tailored for application domain of interest
  • Also much current interest in specialized CPUs for supporting “agentic AI” (to support planning, orchestration, tool use, …., e.g. NVIDIA Vera CPU, ARM AGI CPU)
